# Архитектура sing-box вокруг nodes-tester

Документ объясняет инфраструктуру, в которую встроен тестер нод: клиенты, домашний роутер, DNS и выходные ноды. Это справочный снимок от 2026-08-20, а не инструкция по развёртыванию. Рабочие конфиги находятся в соседнем проекте `sing-box-config` и могли измениться.

Значения вида `<...>` заменяют домены, идентификаторы профилей и имена клиентов.

## Короткая модель

1. Клиентский sing-box принимает трафик через TUN, резолвит домен и выбирает зону.
2. Клиент подключается к роутеру с учётными данными выбранной зоны.
3. Роутер решает, отправить трафик через exit-ноду или напрямую.
4. `nodes-tester` переключает отдельный селектор `nodes-tester` и проверяет каждую ноду через локальный SOCKS5-вход.

Перед изменением конфигурации сверяйте этот документ с текущими файлами `sing-box-config`.


## 1. Топология и роли

```
[приложение на устройстве]
   │  (DNS hijack + локальный резолв на каждом хопе → наружу идёт IP, не имя)
   ▼
[КЛИЕНТ: полноценный sing-box]         ← напр. телефон, <user>.json
   │  TUN → классификация по зоне → naive/vless с credential зоны
   ▼
[РОУТЕР: sing-box на OpenWrt]          ← base.json (+ nodes.json), <router-domain>
   │  одновременно: сервер (inbounds), прозрачный прокси (TUN для LAN), клиент (outbounds)
   │  маршрутизация по auth_user / rule_set / source_ip
   ▼
[ВЫХОДНАЯ НОДА (exit VPS)]             ← *-auto-out (селекторы/urltest из nodes.json)
   │
   ▼
[интернет]
```

Опорные факты:
- **Роутер - это «выходная нода» с точки зрения клиента.** Клиент туннелирует на роутер,
  роутер уже сам выбирает реальную exit-ноду (или выпускает `direct` со своего домашнего IP).
- **Клиент - не «тонкий», а полноценный sing-box**: со своим TUN, DNS-движком, классификацией.
  Резолв делается на клиенте (см. §4), на роутер и ноды уходит уже IP.
- **`<router-domain>` означает роутер** (не exit-нода). naive на :443 (TLS `<domain>`),
  vless/reality на :<port> (`<reality-sni>`).

## 2. Сборка конфигов

- `base.json` - статическая часть роутера (inbounds, route/dns правила, rule_set'ы).
- `nodes.json` (или аналог) - набор exit-нод: outbound'ы `*-auto-out` (urltest) и селекторы,
  включая **`nodes-tester`** (селектор над тестируемыми нодами).
- Скрипт **`update-singbox-config.sh`** сшивает `base.json` с нодами и пишет итоговый файл
  `/etc/sing-box/config.json`. **Валидировать надо сшитый файл**, а не голый `base.json`
  (правила ссылаются на `*-auto-out` из нод):
  ```bash
  sing-box check -c /etc/sing-box/config.json
  ```
- Клиентские конфиги: `android_clients/*.json` (по одному на пользователя, и roaming-*),
  `pc_clients/*.json`. Каждый - самостоятельный sing-box.

## 3. Зоны трафика и credential'ы

На роутере в `naive-in`/`vless-in` заведены пользователи-зоны; клиент выбирает зону, роутер
маршрутизирует по `auth_user`.

| Зона (user) | Смысл | Куда на роутере (факт) |
|---|---|---|
| `global` | обычный «зарубежный» трафик | `global-auto-out` (нода) |
| `us` | сервисы, требующие US-выхода | `us-auto-out` (нода) |
| `ru` | RU-сайты, допускающие RU-ноду | `ru-auto-out` (нода) |
| `ru-predef` | RU-сайты, требующие «чистого» RU-датацентр-IP | `ru-predef-out` (нода) |
| `ru-strict` | RU, что нельзя проксировать за рубеж (банки, госуслуги, торренты) | `direct-out` (домашний IP) |
| `ai` | Claude/Gemini/DeepMind | `direct-out` (см. §7 про xbox-dns) |

Классификация может происходить **на клиенте**: rule_set выбирает нужный credential. Второй вариант -
**на роутере** (по rule_set/geoip, для голого LAN-трафика). Для зоны `ru` они сейчас
расходятся: клиент `<user>.json` шлёт RU-приложения в `direct` (см. §6), а роутерное правило
правило `rule_set[ru-app-list…]` с выходом `ru-auto-out` осталось как fallback для неупрощённых клиентов.

## 4. Модель DNS-резолва (важно для понимания «кто резолвит»)

Каждый хоп использует TUN и `hijack-dns` без FakeIP. Механика:
1. Приложение отправляет DNS-запрос. `hijack-dns` передаёт его DNS-движку, а `dns.rules` выбирает
   сервер `dns-*`. Его `detour` отправляет запрос через ноду в NextDNS. Возвращается реальный IP,
   а NextDNS фиксирует географию выхода.
2. Движок кэширует `домен↔IP`.
3. Приложение подключается по IP; в TUN приходит IP.
4. Маршрут матчится по домену из кэша (rule_set'ы работают).
5. Прокси-outbound подключается по этому IP. На следующий хоп уходит IP, а не имя.

Следствия:
- Выходные ноды получают IP, а не имена. DNS не «утекает» на ноду, резолв остаётся под контролем.
- `detour` у `dns-*` серверов выводит запрос через ноду. NextDNS возвращает географически подходящий IP и сохраняет запрос в журнале.
- Исключение - тестер (socks5h, см. §8): он отдаёт имя, резолв там делает нода.
- `action: resolve` / `domain_strategy` не используются и не нужны: IP-путь и так даёт IP.

NextDNS-профили роутера: `dns-global` (`/<id-global>/router`), `dns-us` (`/<id-global>/router-us`),
`dns-ru`/`dns-ru-predef` (`/<id-ru>/router`), `dns-ru-strict` (`/<id-ru-strict>/router`),
`dns-direct` (`/<id-direct>`, без detour, прямой WAN для недоверенных),
`dns-ai` (`xbox-dns.ru`, без detour), `bootstrap` (DoT 9.9.9.9).

## 5. Модель доверия и безопасности (главная недавняя работа)

Exit-ноды - расходуемый ресурс: их IP блокируются ТСПУ после обнаружения. Доступ к нодам зависит от доверия. Недоверенный трафик по умолчанию идёт через домашний `direct`.

Границы доверия на роутере:
- **Credential (`naive-in`/`vless-in`)** задаёт сильную границу. Валидный user получает маршрут на ноды.
- **`tun-in` (голый LAN)** означает недоверенный по умолчанию. Пускается на ноды **только** если
  `source_ip` входит в `192.168.1.0/25` (доверенная зона). Остальной трафик идёт в `direct-out`.

Реализация в `base.json` (fail-safe, инверсией доверенной зоны):
- **route.rules** (после reject, выше нод-правил):
  ```json
  { "type":"logical","mode":"and",
    "rules":[ {"inbound":"tun-in"},
              {"source_ip_cidr":["192.168.1.0/25"],"invert":true} ],
    "outbound":"direct-out" }
  ```
- **dns.rules** (зеркало, после ads-NXDOMAIN):
  ```json
  { "type":"logical","mode":"and",
    "rules":[ {"inbound":"tun-in"},
              {"source_ip_cidr":["192.168.1.0/25"],"invert":true} ],
    "action":"route","server":"dns-direct" }
  ```

DHCP (OpenWrt):
- **Доверенная зона `192.168.1.0/25`** (.1-.126) - статические lease для устройств,
  которым нужны ноды, но которые НЕ умеют аутентифицироваться credential'ом (ТВ, десктоп без sing-box).
- **Недоверенный пул `192.168.1.128/25`** (.128-.254) - динамический, для «новых/неизвестных».
- **Телефоны с sing-box сажать в НЕДОВЕРЕННЫЙ пул**: их personal-профиль всё равно ходит на ноды
  по credential (от IP не зависит), а Knox-контейнер (идёт в обход клиентского sing-box) всплывает
  на роутере как голый LAN и ловится в `direct`.

Слабости/оговорки:
- Доверие по `source_ip` **подделываемо** в LAN (спуфинг IP). Сильная граница - credential;
  жёстче делается привязкой MAC↔IP на файрволе OpenWrt.
- **IPv6 на LAN должен быть выключен** (иначе устройство уйдёт на ноды по v6 мимо IPv4-правил;
  `strategy: ipv4_only` ограничивает только DNS-ответы, не транспорт).
- **Будущее (sing-box не меньше 1.14):** есть `source_mac_address` (+ Neighbor Resolution, на Linux
  автоматически из ARP/DHCP-lease). Тогда доверие можно привязать к **MAC** напрямую, без
  DHCP-пиннинга IP. На текущей версии (<1.14) - только `source_ip_cidr`.

## 6. Модель угроз и защита (небезопасные RU-приложения)

- **Угроза 1:** RU-приложения детектят VPN, определяют выходные IP (ru и global) и сливают их
  в разработку блокировок ТСПУ, после чего IP попадает в бан.
- **Угроза 2:** те же приложения собирают список установленных приложений.

Защита:
- **От угрозы 1:** небезопасные приложения гоняются **всегда `direct`** (домашний IP).
  На недоверенном устройстве **весь** трафик direct (и ru, и global), поэтому приложение видит **один**
  IP. Разницы между маршрутами ru и global нет, поэтому приложение не может определить VPN по разнице IP и не видит ноды.
- **От угрозы 2:** приложения ставятся в **Samsung Knox** (изоляция от `PackageManager`).
- **Побочка Knox** (контейнер идёт мимо клиентского sing-box) закрыта §5: Knox-трафик всплывает
  на роутере в `tun-in` из недоверенного пула и уходит в `direct`.

**Инвариант «RU-приложение целиком в direct»** (приём в `<user>.json`):
`ru-app-list` (legiz-ru) - это набор **package_name RU-приложений**, а НЕ доменов. Правило
Правило `rule_set[…ru-app-list…]` с выходом `direct-out` стоит **выше** любых нод-правил. **Весь** трафик такого
приложения (любые адресаты) идёт direct. Поэтому небезопасное приложение даже в доверенном
профиле не создаёт разницы IP и не видит ноды. (Работает для personal-профиля, где sing-box видит
процесс; Knox - через роутер.)

## 7. Клиент (финальный `<user>.json`, радикально упрощён)

- **Inbound:** только `tun-in`.
- **Зоны/outbound'ы:** `global-out`, `us-out`, `ru-strict-out` (селектор+urltest над naive+vless).
  Зоны `ru`/`ru-predef`/`ai` как отдельные туннели **убраны** - их трафик идёт `direct`.
- **route.rules (суть):**
  - `ads-n-track` использует reject, а `habr` - `global-out`;
  - `rdp/bittorrent` **или** `rule_set[torrent_trackers, ru-app-list, geosite-ru, google-dm,
    google-gemini, claude, ru-also-domains]` использует **`direct-out`** (RU-приложения и AI - напрямую);
  - дома (`wifi_ssid` <домашний SSID>) приватный IP использует `direct`; вне дома - `ru-strict-out`
    (туннель приходит на роутер, там выбирается `direct`, и клиент получает доступ к домашнему LAN в роуминге);
  - `us-domains` использует `us-out`, `geoip-ru` - `direct`, а `final` - `global-out`.
- **DNS:** `bootstrap`; `dns-ru` (`/<id-ru>/<user>`, без detour, прямой резолв RU);
  `dns-global`/`dns-us` (`/<id-global>/<user>`, detour на ноды); `dns-ai` (`xbox-dns.ru`).
  `strategy: ipv4_only`.
- **AI использует direct** (не ноду): `xbox-dns.ru` должен давать рабочий доступ
  к Claude/Gemini с RU-IP. Роутер использует тот же маршрут и `dns-ai`, поэтому правила согласованы.
  Проверяйте это допущение при отладке доступности AI.

## 8. Как встроен ТЕСТЕР НОД (то, ради чего эта справка в nodes-tester)

- На роутере: `nodes-tester-in` - **socks-inbound `127.0.0.1:2080`**.
- route-правило (высоко, до нод-правил): `{ "inbound":"nodes-tester-in", "outbound":"nodes-tester" }`.
- `nodes-tester` - **селектор над тестируемыми нодами** (из `nodes.json`). Тестер python
  переключает активную ноду в этом селекторе (через Clash API `external_controller
  192.168.1.1:9090`) и гоняет замеры.
- Тестер ходит через **`socks5h://127.0.0.1:2080`** и передаёт sing-box **имя хоста**, а не IP.
  Поэтому:
  - `hijack-dns` его **не** трогает (socks5h не порождает DNS-запрос на :53 - имя едет внутри
    SOCKS);
  - имя пересылается на выбранную ноду, **резолв делает нода на своём выходе**.
- Это **намеренно корректно для замера**: домены резолвятся там же, где у реального пользователя
  (на exit-ноде), без DNS-leak на роутер.
- **`dns-nodes-tester` удалён** из `base.json`: правило для `inbound nodes-tester-in` и
  `dns-nodes-tester` никогда не срабатывало из-за socks5h, а профиль `/<id-tester>` был пуст. Это
  ожидаемо, не баг.

Практический вывод для тестера: замеры отражают поведение реальной ноды, включая её DNS/гео;
источник теста - `127.0.0.1` socks; выбор ноды - через Clash API/селектор `nodes-tester`.

## 9. Инварианты и грабли (держать в голове)

- Валидировать **сшитый** конфиг (`base + nodes`), не голый `base.json`.
- Телефоны с sing-box нужно помещать в **недоверенный DHCP-пул `.128/25`**, иначе Knox не перехватывается.
- **IPv6 на LAN - выключен** (иначе обход IPv4-правил доверия).
- Доверие по IP - «мягкое» (спуфится); credential - «жёсткое».
- Резолв выполняется локально на каждом хопе, наружу уходит IP. `action: resolve` не нужен, кроме случаев
  socks5h/FakeIP/отключённого hijack).
- Диапазоны `.0/25` (доверенные) и `.128/25` (пул) вместе полностью покрывают `192.168.1.0/24`.
- Клиентская классификация отличается от классификации голого LAN на роутере: для зоны `ru` они
  сейчас расходятся: клиент использует direct, а роутерный fallback - ноду.

