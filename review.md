# Повторное ревью кода `nodes-tester`

> Исторический документ от 2026-08-31. Большая часть замечаний уже исправлена. Текущее состояние смотрите в [README.md](README.md), закрытые пункты - в [BACKLOG.md](BACKLOG.md), повторную проверку - в [review-2.md](review-2.md).

Ревью охватывало `nodes_tester`, `subscribe`, `naming`, `dashboard`, конфигурацию, документацию и тестовую механику. Код во время проверки не менялся. Вопросы информационной безопасности не входили в область этого ревью.

- P0 - риск потери данных.
- P1 - дефект, который меняет работу системы.
- P2 - качество реализации, измерений или сопровождения.

## Итог

В проекте уже есть хорошая предметная декомпозиция: измерения, рейтинг, переключение,
хранение, мониторинг и генератор подписок разнесены по модулям. Последние изменения
заметно упростили структуру selector-групп и убрали старую двухуровневую ветку тестера.
При этом сейчас есть несколько логических дефектов, способных менять фактическое
поведение системы, терять историю или давать неверные решения по нодам.

Наиболее важные проблемы:

1. Активно используемая нода удаляется из БД вместе со всей историей, если файл
   `nodes.json` не менялся дольше `retention_days`.
2. Из-за кросс-регионального fallback одна нода может быть прямым членом нескольких
   региональных selector-групп; switcher переключает их все, хотя принимает один
   `region`.
3. Частично выполненная цепочка `PUT` всё равно фиксируется как успешная активация.
4. Суточный сброс `pass_no` не сбрасывает cooldown, поэтому старое значение
   `resume_at` переносится на следующий день и даёт десятки лишних пропусков.
5. HTTP-ошибки Clash API не всегда превращаются в `ClashApiError` и могут завершить
   весь процесс вместо отмены одного прохода.
6. Пустой или полностью пропущенный набор тестов считается прошедшим gate, но даёт
   score 0 и записывается как полноценный новый sample.
7. Изменения switcher, сделанные фоновым монитором между проходами, не сохраняются
   сразу и теряются при рестарте.
8. Сборщик трафика очищает память до успешной записи в БД; ошибка записи теряет
   накопленные дельты.

До дальнейшего рефакторинга стоит сначала закрыть пункты P0/P1 и зафиксировать их
автоматическими тестами. Сейчас `python -m unittest discover -v` обнаруживает
`0 tests`: каталог `nodes_tester/tests` содержит runtime-измерения нод, а не тесты
самого проекта.

## P0 - возможна потеря данных активно тестируемых нод

Файлы: `nodes_tester/storage.py:86-138`, `nodes_tester/storage.py:310-342`,
`nodes_tester/runner.py:201-204`, `nodes_tester/runner.py:313-319`.

`last_seen` обновляется только внутри `load_nodes()`. После первого прохода
`maybe_load_nodes()` больше не вызывает его, пока не изменится mtime `nodes.json`.
Через `retention_days` `cleanup()` считает такие ноды устаревшими и удаляет их из
`nodes`, а затем удаляет их результаты, трафик, endpoints, карантин и историю
активаций. Факт регулярного тестирования ноды на `last_seen` не влияет.

Сценарий воспроизведён на временной SQLite-БД: после начальной загрузки, первого
`maybe_load_nodes()`, сдвига времени на 31 день и неизменного файла количество нод
становится равным нулю.

Рекомендации:

- разделить понятия `catalog_seen_at` и `measured_at`;
- на каждом проходе обновлять присутствие CRC, реально полученных из Clash API;
- удалять ноду только если она отсутствует и в актуальном selector, и в актуальном
  каталоге дольше retention-периода;
- переименовать `retention_days` в более точное имя, если он должен означать только
  удержание отсутствующих нод;
- добавить регрессионный тест с неизменным каталогом и несколькими проходами во
  времени.

## P1 - логика переключения неоднозначна для графа selector-групп

Файлы: `subscribe/groups.py:115-133`, `nodes_tester/switcher.py:205-275`.

Для отсутствующего региона `groups.build()` помещает в его selector все доступные
ноды. В результате одна leaf-нода становится прямым членом нескольких региональных
selector-групп. `_chain_pairs()` ищет все selector-группы, содержащие ноду, и
`_activate()` применяет все найденные пары без привязки к переданному `region`.

Сценарий воспроизведён на одной EU-ноде: построенный граф дал три пары -
`eu-auto-out`, `us-auto-out` и `other-auto-out`. Активация EU-кандидата тем самым
может менять выбор в других региональных selector-группах.

Проблему усиливает графовая модель `_chain_pairs()`: если один родительский selector
достижим несколькими путями и не заморожен, для одного selector могут появиться
несколько несовместимых пар; итог зависит от порядка обхода.

Рекомендации:

- не выводить целевую цепочку только из факта членства leaf-ноды;
- передавать switcher точный корневой selector региона либо явную карту
  `region -> selector -> member`;
- считать несколько родителей неоднозначностью и не выполнять переключение без
  выбранной политики;
- отдельно решить семантику пустого региона: общий fallback сохраняет валидность
  конфига, но перестаёт гарантировать региональность маршрута;
- покрыть тестами один регион, пустые регионы, несколько родителей и незамороженный
  верхний selector.

## P1 - частичная цепочка считается успешной активацией

Файл: `nodes_tester/switcher.py:205-252`.

Код корректно не меняет state, если не прошёл ни один `PUT`. Но при успехе хотя бы
одного из нескольких `PUT` он обновляет `active`, таймер, recent, число активаций,
историю и scoreboard. Пометка `ЧАСТИЧНО N/M` остаётся только текстом в консоли.
Фактический граф selector-групп и сохранённое состояние после этого могут расходиться.

Рекомендации:

- определить обязательные шаги цепочки и считать успехом только их полное выполнение;
- после изменений перечитать `current_selection` для каждого selector;
- при частичном результате либо вернуть уже изменённые selector-группы, либо сохранить
  отдельное состояние `degraded/pending`, не объявляя кандидата активным;
- вернуть из `_activate()` структурированный `ActivationResult`, а не кодировать
  результат только печатью.

## P1 - cooldown несовместим с суточным `pass_no`

Файлы: `nodes_tester/runner.py:206-235`, `nodes_tester/runner.py:436-467`.

`pass_no` сбрасывается в полночь, а `_cooldown` продолжает хранить абсолютное в рамках
старого дня `resume_at`. Например, провал на проходе 100 создаёт `resume_at=102`; после
полуночи проход 1 удовлетворяет условию `1 < 102` и нода пропускается почти весь новый
день. Сценарий воспроизведён напрямую на текущей реализации.

Рекомендации:

- лучший вариант - хранить `resume_at` как timestamp или использовать глобальный
  монотонный номер прохода, а суточный номер оставить только для отображения;
- минимальный вариант - сбрасывать `_cooldown` при смене `current_day`;
- объединить cooldown и persistent quarantine в одну модель времени: сейчас одна часть
  измеряется проходами, другая часами.

## P1 - часть ошибок Clash API обходит доменную обработку

Файлы: `nodes_tester/clash_api.py:29-69`, `nodes_tester/clash_api.py:96-106`,
`nodes_tester/runner.py:229-232`.

`_get()` и `_put()` преобразуют только исключения самого сетевого запроса. В методах
`get_proxy()`, `all_proxies()`, `connections()` и `ping()` вызов
`resp.raise_for_status()` находится снаружи этой нормализации. HTTP 500 даёт обычный
`requests.HTTPError`, а цикл runner перехватывает вокруг прохода только
`ClashApiError`. Аналогично не нормализованы ошибки декодирования JSON.

Это подтверждено fake-response со статусом 500: `all_proxies()` выбрасывает
`HTTPError`, не `ClashApiError`.

Рекомендации:

- сделать один внутренний метод request, отвечающий за запрос, статус и JSON;
- наружу выпускать только `ClashApiError` с типом операции и краткой причиной;
- различать временную недоступность API, отсутствие группы и некорректный ответ;
- добавить fake-client тесты для 404, 500, timeout и битого JSON.

## P1 - «нет измерения» смешано с «успешным измерением»

Файлы: `nodes_tester/tests/base.py:43-63`, `nodes_tester/runner.py:150-162`,
`nodes_tester/runner.py:514-524`, `nodes_tester/scoring.py:40-57`,
`nodes_tester/scoring.py:117-132`, `nodes_tester/scoreboard.py:52-92`.

В текущей модели возможны несколько одинаково проблемных путей:

- все тесты пропущены через `every`;
- все имена `tests_enabled` неизвестны и отброшены;
- набор тестов содержит только `connectivity`, который участвует в gate, но не даёт
  ни одного scoring-компонента;
- набор тестов не содержит метрик, которым назначены веса.

Для пустого `tests` `gate_ok()` возвращает `True`, `instant_score()` возвращает
`(0, True, {})`, после чего scoreboard обновляет EWMA, availability и samples, а
cooldown сбрасывается. Регион с `tests_enabled=["connectivity"]` всегда имеет score 0,
поэтому `candidates()` не вернёт ни одной ноды даже при успешной связности.

Рекомендации:

- ввести отдельный исход `not_measured`/`insufficient_coverage`;
- не обновлять EWMA, availability, samples и cooldown, если в проходе нет минимального
  набора свежих метрик;
- валидировать, что эффективный `tests_enabled` каждого региона способен дать score;
- хранить `coverage`, свежесть компонентов и TTL последнего тяжёлого измерения;
- не сравнивать на одной шкале значения с существенно разным покрытием.

## P1 - emergency-состояние сохраняется не в момент изменения

Файлы: `nodes_tester/switcher.py:49-66`, `nodes_tester/switcher.py:110-178`,
`nodes_tester/switcher.py:205-252`, `nodes_tester/monitor.py:60-78`.

`_save_state()` вызывается только в `evaluate_all()` в конце полного прохода. Монитор
может выполнить emergency-переключение или записать `emg_stuck` во время длительного
ожидания `rotation_bound`, когда следующего `evaluate_all()` долго не будет. При
остановке процесса новые `active`, `rotate_deadline`, `recent`, `activations` и
`emg_stuck` теряются.

Рекомендации:

- сохранять state после каждого завершённого изменения;
- лучше централизовать мутацию в одном методе `commit_state_change()`;
- синхронно фиксировать switch state, active-флаг scoreboard и запись activation либо
  явно определять, какой источник является главным после рестарта.

## P1 - сборщик трафика может потерять дельты

Файлы: `nodes_tester/traffic.py:36-40`, `nodes_tester/traffic.py:95-107`,
`nodes_tester/storage.py:168-190`.

`_flush()` сначала формирует строки и очищает оба буфера, затем делает две независимые
записи в SQLite. Любая ошибка после `clear()` теряет накопленные данные. Кроме того,
`stop()` ждёт поток только пять секунд и затем вызывает `_flush()`; если worker ещё
жив, оба потока могут одновременно менять те же буферы.

Рекомендации:

- под lock атомарно менять активный буфер на новый, а очищать старый только после
  успешного commit;
- при ошибке возвращать старые дельты в очередь либо оставлять их для повтора;
- записывать traffic и endpoints одной транзакцией;
- гарантировать завершение worker перед финальным flush либо явно синхронизировать
  stop/flush/poll.

## P1 - возможен цикл без паузы при просроченном rotation deadline

Файлы: `nodes_tester/runner.py:259-298`, `nodes_tester/runner.py:300-305`.

Если selector временно пуст, `_run_pass()` возвращается до `evaluate_all()`. При этом
загруженный из state активный регион может иметь уже просроченный `rotate_deadline`.
`_wait_for_rotation()` сразу возвращает, после чего цикл немедленно снова запрашивает
пустой selector. Аналогичная ситуация возможна, когда кандидатов нет и старый deadline
не обновляется.

Рекомендации:

- ввести минимальный retry interval для пустого/неполного прохода;
- различать `pass_completed`, `no_nodes`, `api_unavailable`, `no_candidates`;
- обновлять или временно игнорировать просроченный deadline, если выполнить ротацию
  невозможно;
- при `switching.enabled=false` проверять сочетание `loop=true`,
  `rotation_bound=true`, `pass_pause=0`, иначе проходы также идут без паузы.

## P2 - тестовая механика и качество измерений

Подробный предметный разбор находится в `nodes_tester/TESTING_IMPROVEMENTS.md`.
Ниже - дефекты, непосредственно влияющие на текущую реализацию.

### Ошибка одного теста может оборвать весь runner

Файлы: `nodes_tester/runner.py:385-424`, `nodes_tester/runner.py:488-527`.

`test.run()` вызывается без изоляции исключений, а session закрывается не через
`finally`. Неожиданная ошибка теста оставляет session открытой и выходит за пределы
прохода; верхний цикл нормализует только `ClashApiError`. Тяжёлая фаза повторяет тот
же шаблон.

Стоит сделать единый `execute_test()` с `try/finally`, временем выполнения и
структурированным результатом ошибки. Лёгкая и тяжёлая фазы должны использовать один
построитель записи.

### После hard fail продолжаются все тесты

Файл: `nodes_tester/runner.py:518-522`.

После подтверждённого провала connectivity всё равно выполняются latency, jitter,
download и reachability. Нужен staged pipeline: быстрый gate, затем стандартные тесты,
затем тяжёлая фаза только для пригодных кандидатов.

### Имена метрик шире их реального смысла

Файлы: `nodes_tester/tests/latency.py`, `nodes_tester/tests/jitter.py:21-53`.

`latency` измеряет HTTP TTFB, а `jitter` - стандартное отклонение нескольких HTTP
TTFB. `loss_pct` является долей неудачных HTTP-запросов, а не потерей сетевых пакетов.
Точнее назвать их `http_ttfb_ms`, `ttfb_spread_ms` и `request_failure_pct`.

### Download не гарантирует измерение заданной длительности

Файлы: `nodes_tester/tests/download.py:30-67`, `nodes_tester/tests/_stream.py:25-73`.

Быстрая нода заканчивает файл намного раньше `duration`. Медленная нода, стабильно
передававшая данные до лимита времени, получает неполную загрузку и fail при наличии
`Content-Length`. Первое окно искажено стартовым разгоном соединения. Кроме того,
любой `HTTPError`, а не только документированные 429/5xx, помечается как
`server_limit` и превращается в `ok=true`.

Нужно разделить `transport_ok`, `completed`, `duration_reached` и
`throughput_acceptable`, классифицировать конкретные HTTP-статусы и сравнивать
несколько устойчивых окон после стартового.

### Reachability имеет слишком слабый критерий успеха

Файл: `nodes_tester/tests/reachability.py:32-64`.

Достаточно ответа одной цели из списка, а любой статус `<500` считается успехом.
Это доказывает лишь частичную HTTP-доступность. Нужны правила по endpoint: допустимые
статусы, ожидаемый ответ, критичность и минимальный кворум. Один общий
`requests.Session` одновременно используется worker-потоками; проще и понятнее дать
каждому probe независимый клиент с общей неизменяемой конфигурацией.

### Connectivity принимает нераспознанный ответ

Файл: `nodes_tester/tests/connectivity.py:67-85`.

HTTP-успех остаётся `ok=true`, даже если парсер тела не смог подтвердить `exit_ip`.
Нужно отдельно возвращать `transport_ok` и `identity_parsed`, а для hard gate
определить обязательные поля.

### Нет проверки параметров тестов

Файлы: `nodes_tester/tests/base.py:43-63`, `nodes_tester/tests/jitter.py:21-37`,
`nodes_tester/tests/download.py:30-36`, `nodes_tester/tests/reachability.py:32-49`.

Нулевые или отрицательные `samples`, `workers`, `duration`, `timeout`,
`window_bytes` и интервалы приводят к исключениям или бессмысленным результатам.
Валидацию лучше выполнять один раз при загрузке конфигурации каждого теста.

## P2 - scoring и scoreboard

### Отсутствующие компоненты меняют смысл общей шкалы

Файл: `nodes_tester/scoring.py:59-132`.

Вес отсутствующей метрики исключается из знаменателя. Поэтому score 80 с двумя
компонентами выглядит равным score 80 с шестью компонентами. Для принятия решений
нужны либо обязательный профиль метрик, либо отдельные score и показатель confidence.

### Два threshold не используются

Файлы: `nodes_tester/config.py:139-147`, `nodes_tester/scoring.py:59-115`.

`hold_min` и `hold_target` присутствуют в коде, схеме и обоих конфигах, но не участвуют
в расчёте. Их следует либо подключить к нормализации `hold_ratio`, либо удалить.

### Равные границы маскируют ошибку конфигурации

Файл: `nodes_tester/scoring.py:25-38`.

При `good == bad` функции возвращают 1.0. Это превращает неверную пару порогов в
идеальный результат. Лучше отклонять такую конфигурацию до запуска.

### Scoreboard не синхронизирован между потоками

Файл: `nodes_tester/scoreboard.py:33-169`.

Комментарий опирается на снимок `list(...)` и GIL, но значения словаря остаются
изменяемыми. `record()`, `set_active()`, `set_heavy()` и `write()` могут выполняться
параллельно с монитором. Возможны потеря active-флага или несогласованная строка CSV.
Нужен lock вокруг составных чтений/изменений и возврат копий строк наружу.

Дополнительные упрощения:

- `end_pass(pass_no)` не использует аргумент;
- `_pass_no` через property скрывает простой `_current_pass`;
- `last_seen` хранит суточный номер прохода, который сбрасывается, хотя имя похоже на
  timestamp;
- словари строк лучше заменить `NodeScore` dataclass и сериализатором CSV.

### Heavy-veto имеет неочевидную политику

Файлы: `nodes_tester/runner.py:185-186`, `nodes_tester/runner.py:364-424`,
`nodes_tester/scoreboard.py:115-146`.

- TTL устанавливается один раз из base-параметров; региональный override
  `heavy_veto_hours` игнорируется, хотя `heavy_candidates` применяется по регионам.
- Если все здоровые кандидаты vetoed, `candidates()` возвращает их обратно. Это
  разумный fallback, но слово `veto` обещает более жёсткое поведение.
- heavy-запись не содержит timestamp, provider, protocol, country и region_group,
  поэтому файловый отчёт получает неполные строки.

Стоит сделать политику явной (`hard`, `fallback_if_empty`, `expired_only`), хранить TTL
на строке/регионе и использовать общий построитель record.

## P2 - конфигурация

Файлы: `nodes_tester/config.py:269-402`, `config/config.schema.json`.

Runtime-валидация проверяет только часть ограничений, а JSON Schema применяется лишь
при наличии необязательного `jsonschema`. В проверенном окружении эта зависимость не
установлена, поэтому фактически работает только `_validate()`.

Не проверяются, среди прочего:

- `alpha`, `avail_floor`, `avail_full`, отрицательные weights и порядок thresholds;
- `confirm_cycles`, `monitor.fails`, `rotation.top_k`, `avoid_recent`;
- `rotation.interval`, `jitter <= interval`, `min_dwell`, cooldown;
- интервалы traffic, `garbage_hours`, `max_skip`;
- эффективные региональные/group override, включая неизвестные ключи;
- зависимости `monitor -> switching -> scoring` и `load_balance -> storage`.

Отдельные проблемы интерфейса конфигурации:

- `_section()` превращает любое falsy-значение в `{}`, поэтому, например, `false`
  не диагностируется как значение неверного типа;
- неизвестные поля run молча отбрасываются ради совместимости и скрывают опечатки;
- `testing_groups` - список, но весь runner использует только первый элемент;
- `region_groups.enabled` нигде не влияет на поведение;
- комментарии продолжают говорить о «двухуровневом тестировании», хотя структура
  selector-групп теперь плоская.

Рекомендация: иметь одну обязательную точку полной семантической валидации уже
собранного effective config. Устаревшие ключи лучше обрабатывать явной миграцией с
предупреждением, а не общим молчаливым фильтром.

## P2 - host-aware планирование

Файлы: `nodes_tester/runner.py:90-148`, `nodes_tester/storage.py:140-145`.

Если endpoint отсутствует в storage, `_host_of()` объединяет все ноды одного
провайдера как один физический хост. Это может давать ложные паузы между независимыми
серверами. При пустом provider fallback по CRC, наоборот, не распознаёт общий хост.
Поведение min-host-gap поэтому сильно зависит от полноты `nodes` и корректности CRC.

Также timestamp записывается перед выполнением теста, то есть gap - start-to-start,
а не пауза после завершения предыдущей нагрузки. Это допустимо, но должно быть
сформулировано явно.

Рекомендации:

- хранить статус `endpoint_known` и не выводить физическую эквивалентность из
  provider;
- логировать долю нод с реальными endpoint;
- оформить `EndpointKey(host, port, protocol)` отдельным типом;
- заменить цикл `while any(dqs)` на deque активных корзин без повторного просмотра
  уже пустых очередей.

## P2 - хранилище и отчёты

### История живых нод растёт без ограничения

Файл: `nodes_tester/storage.py:310-339`.

Retention удаляет только исчезнувшие ноды и не ограничивает `results`, `traffic`,
`endpoints` и `activations` живых нод. Дашборд агрегирует весь traffic history на
каждом обновлении. Нужны отдельные сроки хранения сырых фактов и периодические
rollup-таблицы.

### Невалидный CRC всё равно становится ключом истории

Файл: `nodes_tester/storage.py:105-137`.

При несовпадении рассчитанного CRC с CRC в теге устанавливается `crc_ok=0`, но строка
всё равно вставляется под ошибочным ключом. Несколько таких outbound могут смешать
метаданные и факты. Следует не использовать неподтверждённый идентификатор как
авторитетный ключ либо помещать запись в отдельный диагностический набор.

### Ручной cascade хрупок и плохо масштабируется

Файл: `nodes_tester/storage.py:320-339`.

Каждую новую таблицу нужно не забыть добавить в список удаления. Большой список stale
CRC также может превысить лимит параметров SQLite. Нужны batch-delete и явная модель
связей/миграций; `PRAGMA user_version` упростит дальнейшее развитие схемы.

### Newest-first отчёт даёт квадратичный объём I/O

Файл: `nodes_tester/reporter.py:47-100`.

При каждом flush весь старый файл читается и переписывается. С ростом истории общая
работа становится O(n²). Практичнее append-only, ротация по дате/размеру и
newest-first только при чтении. Повреждённый старый JSON сейчас молча заменяется новым
списком; это лучше диагностировать отдельно.

## P2 - dashboard

Файлы: `dashboard/data.py`, `dashboard/server.py`, `dashboard/__init__.py`.

1. Запрос latest result соединяет строки по `MAX(ts)`. Timestamp имеет секундную
   точность, поэтому две записи одного теста в одну секунду дают дубликаты. Нужен
   первичный `result_id` или оконная функция с однозначным tie-breaker.
2. Для строки ноды `ts=max(ts)` и `pass_no=max(pass_no)` считаются независимо. После
   суточного сброса можно показать дату свежего результата вместе со старым большим
   номером прохода. Номер следует брать из той же строки, что дала максимальный ts.
3. Endpoint-трафик тестера фильтруется через `source_ip <> '127.0.0.1'`, хотя collector
   уже знает `is_tester`, но таблица endpoints этот признак не хранит. Такая эвристика
   может одновременно скрывать обычный трафик и показывать тестовый.
4. Каждый авто-refresh открывает БД и заново агрегирует всю историю. При нескольких
   клиентах `ThreadingHTTPServer` дублирует работу. Нужен snapshot/TTL-cache и
   ограниченные временные окна.
5. `dashboard/__init__.py` утверждает, что читает `switch_state.json`, но `collect()`
   его не использует.
6. `emergency-stuck` записывается в таблицу activations и отображается как последнее
   «переключение», хотя фактической смены ноды не было. Лучше разделить события и
   переходы состояния.
7. HTML, CSS и JavaScript находятся одной строковой константой в Python. Разделение
   на template/static-файлы заметно упростит чтение и проверку интерфейса.

## P2 - генератор подписок и парсеры

### Один и тот же pipeline продублирован в нескольких местах

Файлы: `subscribe/main.py:190-268`.

Преобразование tuple-результатов ShadowTLS в плоский список скопировано для base64,
Clash, plain text, локального файла и Happ. Стоит выделить:

```text
source -> fetch/decode -> detect format -> parse -> flatten -> normalize
```

и иметь одну функцию `_flatten_nodes()`.

### `process_subscribes()` изменяет входной конфиг

Файл: `subscribe/main.py:28-64`.

При `subgroup` поле `subscribe['tag']` изменяется на месте. Повторный вызов на том же
объекте дописывает suffix ещё раз. При этом `_provider` записан до изменения tag, так
что provider в метаданных и ключ результата расходятся. Нужен локальный
`effective_tag` без мутации входа.

### Пустой удалённый ответ имеет два разных представления

Файлы: `subscribe/main.py:208-238`, `subscribe/main.py:311-375`.

Неудачная загрузка обычно возвращает `''`, а whitespace-only ответ - `None`, после
чего `parse_content(None)` вызывает исключение. Повтор с User-Agent `clashmeta` также
не проверяет `response is None`. Источник должен возвращать один тип результата,
например `FetchResult`, а пустое содержимое - всегда нормальную пустую строку/список.

Повторные запросы теряют исходный custom User-Agent, а `pass` после сообщения об
окончательной ошибке ничего не делает и затрудняет чтение потока управления.

### Определение формата по подстроке ненадёжно

Файл: `subscribe/main.py:347-375`.

Условия `'proxies' in response_text` и `'outbounds' in response_text` могут сработать
на обычном тексте. Удаление JSON-комментариев через `re.sub(r'//.*', '', text)` ломает
строки URL: `{"url":"https://..."}` превращается в оборванный JSON; это также
воспроизведено отдельно.

Нужно сначала пробовать конкретные парсеры по структуре, а поддержку JSONC реализовать
полноценным tokenizer либо убрать.

### Локальные форматы поддерживаются непоследовательно

Файл: `subscribe/main.py:378-395`.

Специально распознаётся только `.yaml`; `.yml` и локальный sing-box JSON идут как
обычный список share-links и обычно дают пустой результат. Лучше определять формат по
содержимому с расширением как подсказкой.

### Фильтрация имён сложнее необходимого

Файл: `subscribe/main.py:181-187`.

Тройной цикл с удалением из копии списка заменяется одной фильтрацией через `any()`.
Пустой токен после split сейчас совпадает с каждым tag и может удалить все ноды;
токены нужно очищать и отбрасывать до фильтрации.

### Конкретные логические дефекты парсеров

- `subscribe/parsers/trojan.py:38-54`: `type=ws` без параметра `host` вообще не
  создаёт `transport`, хотя тип транспорта известен.
- `subscribe/parsers/https.py:21-23`: учётные поля добавляются только при
  `remark[0].count('@') == 2`; обычная форма `user:password@host:port` содержит один
  символ `@`, поэтому поля теряются.
- `subscribe/parsers/wg.py:31-39`: отсутствие `ip/address` даёт `TypeError` вместо
  контролируемого отклонения строки.
- `subscribe/parsers/clash2base64.py:309-343`: HTTP/SOCKS запись с username и без
  password вызывает `KeyError`; это воспроизведено для обоих типов.
- `subscribe/parsers/http.py:20-28`: outbound типа `http` всегда создаётся с
  включённым TLS независимо от семантики входной схемы; plain HTTP тем самым меняет
  протокол.
- во многих parser-файлах отсутствует единый контракт: одни возвращают `None`, другие
  tuple, третьи выбрасывают разные исключения. Это и создаёт большое количество bare
  `except` в вызывающем коде.

Рекомендация: общий `ParseResult(nodes, warnings)` и table-driven тесты всех
поддерживаемых форм URI, включая неполные, но синтаксически допустимые варианты.

### Плоские импорты и глобальное состояние усложняют тестирование

Файлы: `subscribe/__main__.py:1-16`, `subscribe/main.py:1-21`,
`subscribe/groups.py:34-71`.

`sys.path` настраивается вручную, parsers и providers лежат в globals, group params
перезагружают набор module-level переменных. Лучше перевести импорты на package-relative,
а настройки - в `GroupConfig`/`SubscriptionContext`, передаваемые явно.

### Есть неиспользуемый legacy-код

Подтверждены определения без вызовов в проекте:

- `subscribe/tool.py`: `saveFile`, `firstLine`, `is_ip`, `filterNodes`, `replaceStr`,
  `removeNodes`, `prefixStr`;
- `nodes_tester/clash_api.py`: `selector_groups_with_member`;
- `nodes_tester/storage.py`: `active_garbage`;
- `naming/identity.py`: `region_label` после удаления `by_selector`.

После добавления тестов их стоит удалить. Также нужно убрать закомментированные старые
ветки, объединённые импорты в одной строке, bare `except` и комментарии-заглушки вроде
`#fuck`: они заметно ухудшают читаемость парсеров.

## P2 - идентичность и имена

Файл: `naming/identity.py`.

`parse_node()` и `parse_group()` вынуждены восстанавливать структуру из строки с
эвристиками. Provider может содержать дефис и совпадать с токеном протокола; например,
суффикс provider `-vless` неоднозначен для `parse_group()`. Сейчас новые плоские группы
уменьшили число таких случаев, но traffic продолжает разбирать старые failsafe-теги.

Надёжнее хранить явную карту tag -> identity/region/provider рядом с generated config,
а строковый парсер оставить только как compatibility fallback. `NodeIdentity` можно
сделать `frozen=True`, а CRC проверять по ожидаемому формату перед использованием как
ключа.

## Возможности упрощения архитектуры

### Разделить `Runner`

`nodes_tester/runner.py` содержит 557 строк и одновременно отвечает за жизненный цикл,
планирование, host-gap, выбор тестов, light/heavy execution, cooldown, quarantine,
reporting и восстановление selector. Многие поля (`_base`, `_cooldown`, `_endpoints`,
`_host_ep_last`, caches) появляются только внутри `run()`, хотя используются другими
методами.

Практичное разделение без чрезмерной абстракции:

- `RunState` - текущий день/проход, caches, cooldown, endpoints;
- `NodePlanner` - enumerating и host-aware order;
- `TestExecutor` - выбор selector, session, staged tests, record;
- `CooldownPolicy` - backoff/quarantine по времени;
- `PassScheduler` - loop/pass pause/rotation deadline;
- `Runner` - только связывает эти части.

### Ввести типы вместо неформальных tuple/dict

В коде часто используются `list[tuple]`, `dict`, `cand["node"]`,
`(region, ident)`, `(server, port)`. Небольшие dataclass-типы `PlannedNode`,
`Endpoint`, `TestExecution`, `ActivationResult`, `NodeScore`, `FetchResult` уменьшат
число скрытых договорённостей и сделают функции самодокументируемыми.

### Централизовать время и внешние зависимости

Логика смешивает `time.time()`, `time.monotonic()`, локальную дату и суточный номер
прохода. Интерфейсы `Clock`, `RandomSource`, `ClashGateway`, `ResultStore` упростят
детерминированные тесты cooldown, rotation и retention. Полноценный DI-фреймворк не
нужен - достаточно аргументов конструктора с разумными default.

### Один источник истины для результата и active state

Сейчас состояние распределено между `score.csv`, `switch_state.json`, SQLite и
фактическими selector-группами. Следует письменно определить приоритет восстановления
и момент согласования. Внутри процесса лучше оперировать типизированным snapshot, а
файлы считать представлениями, а не независимыми mutable state.

### Упростить dashboard presentation

Форматирование одного теста продублировано в `_summary()` runner и `_cell()` dashboard.
Тест может предоставлять display metadata/formatter либо использоваться единый
presentation-модуль. Это исключит ручное изменение двух мест при добавлении теста.

## Автоматические тесты, которые нужны в первую очередь

### P0/P1 regression suite

1. Неизменный `nodes.json` и активные проходы дольше retention не удаляют ноду.

8. Ошибка storage во время traffic flush не теряет буфер.

1. Пустой, неизвестный и полностью `every`-пропущенный набор тестов - not measured.

4. Coverage/TTL компонентов и региональный heavy-veto.
5. Смена дня, рестарт, quarantine trial и успешное восстановление.

### Runtime-тесты нод

1. Fake HTTP responses для каждого статуса download.
2. EOF раньше duration, duration cap, Content-Length отсутствует/не совпадает.

5. Reachability: пустой список, частичный кворум, разные правила endpoint.
6. Неожиданное исключение одного теста не отменяет обработку остальных нод.

### Subscribe/naming/dashboard

1. Table-driven URI tests для каждого parser.
2. Whitespace/empty response, `.yaml`, `.yml`, JSON, plain links и base64.
3. JSON с URL при обработке комментариев.
4. `process_subscribes()` идемпотентен и не меняет вход.
5. ShadowTLS flatten и detour mapping при повторяющихся исходных именах.
6. Пустой регион, один регион, все регионы, несколько родителей selector.
7. Последняя result-строка при одинаковом `ts` и pass label на границе суток.
8. Round-trip/property tests для generated node tag и `parse_node()`.

  `heavy_download`, `jitter`, `latency`, `reachability`.
