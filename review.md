# Code review проекта `nodes-tester`

Дата ревью: 2026-08-18  
Объём: пакеты `nodes_tester`, `subscribe`, `naming`, конфигурация, схема, документация и зависимости.  
Исходный код в рамках ревью не изменялся.

## Итог

Архитектура основной части тестера в целом понятна и удачно разделена: Clash API, тесты, хранение, рейтинг, переключение и мониторинг находятся в отдельных модулях. Есть атомарная запись отчётов и состояния, блокировка SQLite, централизованная модель идентичности нод и разумное восстановление тестовых selector-групп.

Однако перед эксплуатацией конвертера подписок на недоверенных источниках и перед включением автоматического боевого переключения нужно устранить критические и высокоприоритетные проблемы. Главные риски:

- удалённое выполнение произвольного Python-кода из содержимого подписки;
- возможная публикация secret, subscription URL и реквизитов нод в Git;
- потеря рабочего `nodes.json` при ошибке записи;
- ложная фиксация успешного боевого переключения при нуле выполненных `PUT`;
- молчаливое дублирование нод после ошибки одного из парсеров;
- фактический сетевой таймаут загрузки подписки до 5000 секунд на попытку;
- полное отсутствие автоматических регрессионных тестов.

Рекомендуемый статус: **не выпускать в unattended/production-режим до исправления P0 и P1**.

## Найденные проблемы

### P0 — `eval()` исполняет данные из удалённой подписки

Файлы: `subscribe/parsers/ss.py:63`, `subscribe/parsers/ss.py:134`.

Парсер Shadowsocks декодирует параметр плагина из URL подписки и передаёт полученную строку в `eval()`. URL подписки является недоверенным удалённым вводом. Злоумышленник или скомпрометированный провайдер может поместить туда Python-выражение с побочными эффектами и выполнить код с правами процесса конвертера. Это даёт доступ как минимум к конфигам и секретам на машине, а при привилегированном запуске — к системе.

Рекомендации:

1. Полностью удалить оба `eval()`.
2. Для JSON использовать `json.loads`; для legacy-представления Python-словаря, если оно действительно требуется, временно допустим `ast.literal_eval` с обязательной проверкой, что результат — `dict` со строго разрешёнными ключами и скалярными значениями.
3. Ограничить длину декодированного параметра и допустимые значения `mode`, `tls`, `mux`, `version`, `port` и т. п.
4. Добавить security-тесты с выражениями вроде вызова функции, импортов и вложенных объектов; парсер должен отклонять их без выполнения.

### P0 — секретные рабочие конфиги не исключены из Git

Файлы: `.gitignore:1-12`, `config/config.json:5`, `config/providers.json:4`, `config/user_nodes.json:7` и другие чувствительные поля этих файлов.

Текущий `.gitignore` исключает результаты, БД, виртуальные окружения и IDE, но не исключает рабочие файлы в `config/`. `git status --untracked-files=all config` показывает `config/config.json`, `config/providers.json` и `config/user_nodes.json` как готовые к добавлению. При этом в них присутствуют Clash API secret, URL подписок и реквизиты нод. Достаточно обычного `git add .`, чтобы опубликовать их.

Рекомендации:

1. Немедленно добавить в `.gitignore` как минимум `config/config.json`, `config/providers.json`, `config/user_nodes.json`.
2. Оставить в репозитории обезличенные `*.example.json`; для providers/user nodes тоже создать примеры без реальных URL и ключей.
3. До первого коммита проверить `git status --untracked-files=all` и `git diff --cached`.
4. Если эти значения уже когда-либо попадали в удалённый репозиторий или логи, отозвать/сменить secret, subscription URL и ключи нод; простого удаления из последнего коммита недостаточно.

### P1 — ошибка парсера повторно добавляет предыдущую ноду или обрывает разбор

Файл: `subscribe/main.py:218-231`.

Переменная `node` не сбрасывается перед каждой итерацией. Исключение из `factory(t)` подавляется через `pass`, после чего выполняется `if node`. Если ранее нода уже была успешно разобрана, она добавляется повторно вместо ошибочной. Если исключение случилось на первой поддерживаемой строке, обращение к `node` приводит к `UnboundLocalError` и прерывает весь разбор.

Рекомендация: перед `try` делать `node = None`, а в `except` логировать протокол/номер строки и выполнять `continue`. Желательно считать число отброшенных строк и завершаться с ненулевым кодом либо явным предупреждением, если доля ошибок превышает установленный порог.

### P1 — генерация `nodes.json` не атомарна и может удалить рабочий конфиг

Файлы: `subscribe/main.py:338-353`, `subscribe/tool.py:8-11`.

`save_config` сначала переименовывает в backup или удаляет существующий файл, затем открывает итоговый путь напрямую. Ошибка диска, прав доступа, нехватка места, прерывание процесса или ошибка сериализации после удаления оставит production без актуального `nodes.json` либо с частично записанным JSON. Значение `auto_backup=false` делает потерю особенно прямой.

Рекомендации:

1. Сериализовать данные до любых операций с целевым файлом.
2. Записать во временный файл в том же каталоге, выполнить `flush` и при необходимости `os.fsync`, затем заменить цель через `os.replace`.
3. Backup создавать копированием или атомарным переименованием только в согласованной последовательности; не удалять цель заранее.
4. Перед заменой валидировать сгенерированный fragment (как минимум повторным `json.loads`, лучше `sing-box check/merge` в deployment-процессе).

### P1 — switcher объявляет ноду активной даже при неуспешном переключении

Файл: `nodes_tester/switcher.py:156-185`.

`_activate` выполняет цепочку `PUT`, но ошибки отдельных запросов только печатает. После цикла состояние безусловно обновляется: `active`, таймеры, счётчик активаций и scoreboard меняются даже при `done == 0` или частичном успехе. В результате монитор и оператор считают ноду активной, хотя боевые selector-группы могли остаться на старой ноде. Это также запускает cooldown и откладывает следующую попытку.

Рекомендации:

1. До переключения построить ожидаемую цепочку; отсутствие цепочки считать ошибкой конфигурации.
2. Обновлять persistent state только после успешного выполнения всей обязательной цепочки и последующей проверки `current_selection`.
3. При частичном успехе либо откатить уже изменённые selector-группы, либо явно сохранить состояние `degraded/pending` и немедленно повторить сверку.
4. Возвращать структурированный результат переключения, а не только печатать `PUT {done}`.

### P1 — таймаут HTTP-загрузки подписки равен 5000 секундам

Файлы: `subscribe/tool.py:352-365`, `subscribe/main.py:251-270`.

В `requests` параметр `timeout=5000` измеряется в секундах, а не миллисекундах. С учётом первоначального запроса и до десяти повторов одна зависшая подписка теоретически способна блокировать процесс много часов. Все исключения при этом подавляются без диагностики; повторы после первого запроса теряют настроенный User-Agent.

Рекомендации:

1. Использовать раздельный timeout, например `(5, 30)` для connect/read, вынести его в конфигурацию.
2. Ограничить число повторов (обычно 2-3), применять exponential backoff с jitter и сохранять custom User-Agent во всех попытках.
3. Логировать класс ошибки без раскрытия полного URL/токена подписки.
4. Ограничить максимальный размер ответа и число обрабатываемых нод.

### P1 — нет автоматических тестов для критической логики

Каталог `nodes_tester/tests` содержит runtime-проверки прокси, но не unit/integration tests проекта. `python -m unittest discover -v` завершился сообщением `Ran 0 tests`.

Особенно рискованно отсутствие тестов для парсеров недоверенного ввода, переименования/detour, CRC, score/gate, многоуровневой цепочки switcher, атомарной записи и восстановления после сетевых ошибок.

Минимальный набор:

- table-driven тесты всех схем URI каждого протокола, включая битые и злонамеренные строки;
- регрессия для `parse_content`: успешная строка + ошибочная строка не должны дублировать результат;
- property/fuzz tests: любой ввод парсера либо даёт валидный dict, либо контролируемую ошибку, но не выполняет код и не зависает;
- fake Clash API для полного успеха, частичного успеха, 404/500/timeout и проверки rollback/state;
- тесты атомарной записи при исключении между созданием temp-файла и `os.replace`;
- тесты `scoring` на границах thresholds и восстановление scoreboard/state после рестарта;
- SQLite tests на retention, CRC mismatch и конкурентную запись.

### P2 — `requests.Session` используется параллельно несколькими потоками

Файл: `nodes_tester/tests/reachability.py:32-50`.

Один `ctx.session` передаётся всем worker-потокам `ThreadPoolExecutor`. `requests.Session` содержит изменяемое состояние и не предоставляет явной гарантии thread safety для совместного использования. Сейчас cookies почти не нужны, но поведение может стать нестабильным при редиректах, auth/cookie-ответах или будущих изменениях.

Рекомендация: создавать отдельную session на worker/запрос с теми же proxy/auth-настройками либо использовать явный пул адаптеров без общего mutable session. `workers` также нужно валидировать как число `>= 1`.

### P2 — streaming response закрывается не во всех ветках исключений

Файлы: `nodes_tester/tests/download.py:26-35`, `nodes_tester/tests/_stream.py:30-50`.

Если `raise_for_status()` или `iter_content()` бросит исключение, `resp.close()` не выполняется. При длинном цикле это способно удерживать соединения/дескрипторы и ухудшать последующие измерения.

Рекомендация: использовать `with session.get(..., stream=True) as resp:` либо `try/finally`. Аналогичный шаблон стоит применять последовательно ко всем HTTP-ответам.

### P2 — отчёты newest-first переписываются целиком на каждом прогоне

Файл: `nodes_tester/reporter.py:46-108`.

Для `jsonl`, `json` и `csv` старый файл полностью читается и полностью перезаписывается при каждом flush. В непрерывном режиме стоимость растёт линейно с историей, а суммарная стоимость и износ диска — квадратично по числу прогонов. Ограничения размера/retention для файлового отчёта нет.

Рекомендация: писать append-only oldest-first, а newest-first предоставлять на уровне чтения/запроса; либо ротировать файлы по дате/размеру и задать retention. SQLite уже лучше подходит для сортировки по времени.

### P2 — runtime-валидация конфигурации покрывает лишь несколько полей

Файл: `nodes_tester/config.py:232-320`.

JSON Schema есть, но `load_config` её не применяет. `_validate` проверяет только selector group, порт, recognition и report format. Отрицательные интервалы, `rounds <= 0`, `workers <= 0`, неверные URL, `confirm_cycles <= 0`, некорректные веса/thresholds, `retention_days < 0` и противоречивые сочетания флагов проходят до runtime. В частности, отрицательный retention сдвинет cutoff в будущее и удалит всю историю при `prune()`.

Рекомендации:

1. Валидировать конфиг по `config.schema.json` при загрузке (и держать схему синхронной с dataclass).
2. Добавить семантические проверки диапазонов и зависимостей между секциями.
3. Не молча отбрасывать неизвестные override-поля в `RunParams.merged`; считать это ошибкой конфигурации.

### P2 — зависимости не воспроизводимы и локальное окружение не готово к полной проверке

Файл: `requirements.txt:1-10`.

Зависимости заданы только нижними границами, без lock-файла и хешей. Это допускает неожиданные несовместимости при следующей установке. В текущем workspace `.venv/Scripts/python.exe` не запускается, а системный Python не содержит `PySocks`, `PyYAML` и `ruamel.yaml`; поэтому end-to-end запуск `subscribe` сейчас невозможен без восстановления окружения.

Рекомендации: зафиксировать поддерживаемые версии через lock/constraints, добавить CI-матрицу для заявленных версий Python и команду bootstrap/check окружения. README также следует поправить: в разделе установки перечислены только `requests` и `PySocks`, хотя `subscribe` требует две YAML-библиотеки.

## Дополнительные замечания

- Многочисленные bare `except:` в `subscribe` скрывают `KeyboardInterrupt`, программные ошибки и причины потери нод. Ловить следует конкретные исключения (`ValueError`, `UnicodeDecodeError`, `requests.RequestException` и т. д.) и вести безопасный структурированный лог.
- Полные subscription URL сейчас печатаются в консоль (`subscribe/main.py:253`, `:319`). Такие URL часто сами являются bearer-секретами. В логах их нужно маскировать, оставляя host и короткий fingerprint.
- В `TrafficCollector.stop()` поток ожидается только 5 секунд, после чего `_flush()` может выполняться одновременно с ещё живым worker-потоком. Нужен гарантированный протокол остановки или синхронизация буферов.
- CRC32 полезен как стабильный короткий fingerprint, но не является collision-resistant идентификатором. Текущий код обнаруживает коллизию тегов в одном прогоне, однако для долговременной БД безопаснее хранить полный SHA-256 payload рядом с короткой отображаемой меткой.
- `scoreboard` полагается на атомарность операций CPython/GIL вместо общей блокировки между runner и monitor. Лучше защищать чтение/изменение `rows` явным lock и возвращать копии строк.
- Отсутствуют CI, lint/type-check и security scan. Практичный минимум: `pytest`, `ruff`, `mypy`/`pyright`, `bandit` или Semgrep rule на `eval`, dependency audit и smoke-test CLI.

## Что сделано хорошо

- Хорошее разделение ответственности основной подсистемы `nodes_tester`.
- `ClashApiClient` централизует auth, отключает environment proxies для локального API и переводит сетевые ошибки в доменное исключение.
- Для report, scoreboard и switch state уже используется temp + `os.replace`.
- SQLite защищён lock, включён WAL, SQL использует параметры, а не конкатенацию пользовательского ввода.
- Общий пакет `naming` уменьшает риск рассинхронизации между генератором тегов и тестером.
- Восстановление исходного выбора тестовых selector-групп находится в `finally`.
- Система рейтинга и переключения отделена от измерений и имеет наблюдаемые промежуточные метрики.

## Рекомендуемый порядок исправлений

1. **Немедленно:** удалить `eval`, исключить и при необходимости ротировать секреты.
2. **До следующего production-запуска:** сделать атомарную генерацию `nodes.json`, исправить `parse_content`, сократить timeout/retry и маскировать URL.
3. **До включения switching:** сделать переключение транзакционным/проверяемым и не менять state при частичном провале.
4. **Затем:** добавить регрессионные unit/integration tests и CI; только после этого рефакторить подавление исключений и конкурентный доступ.
5. **Эксплуатационная устойчивость:** ввести ротацию отчётов, полноценную валидацию конфигурации и воспроизводимое окружение.

## Выполненные проверки и ограничения

- Все Python-файлы успешно прошли `python -m compileall -q naming nodes_tester subscribe` на Python 3.8.3.
- `python -m nodes_tester --list-tests` успешно загрузил реестр и вывел 6 runtime-тестов.
- Все JSON-файлы в `config/` синтаксически валидны.
- `python -m unittest discover -v` обнаружил 0 автоматических тестов.
- Полный сетевой прогон тестера не выполнялся: он меняет реальные selector-группы и требует доступный Clash API/SOCKS endpoint.
- End-to-end запуск `subscribe` не выполнялся из-за отсутствующих YAML-зависимостей в системном Python и неработающего локального `.venv`; выводы по нему получены статическим трассированием конкретных путей выполнения.
- Репозиторий фактически находится в начальном/неиндексированном состоянии: почти все проектные файлы отображаются как untracked, поэтому сравнение с базовой веткой и анализ регрессий по diff невозможны.
