# nodes_tester

`nodes_tester` проверяет уже загруженные в sing-box leaf-ноды, рассчитывает рейтинг,
управляет автоматическим переключением и сохраняет историю в SQLite.

Пакет не загружает подписки и не создаёт конфигурацию sing-box. За это отвечают
[`nodes_fetch`](../nodes_fetch/README.md) и [`nodes_config`](../nodes_config/README.md).

## Как проходит проверка

Для работы нужны:

1. запущенный sing-box 1.14 или новее с API-сервисом (`services[type=api]`);
2. SOCKS5 inbound, через который идёт тестовый трафик;
3. плоский selector `nodes-tester`, содержащий leaf-ноды напрямую;
4. `config.json` с адресами API-сервиса (`box_api`) и SOCKS5.

Для каждой ноды Runner выполняет цикл:

```text
выбрать ноду через API-сервис sing-box
    -> отправить проверки через SOCKS5
    -> сохранить сырые результаты
    -> обновить рейтинг и ограничения
    -> при необходимости переключить рабочий selector
```

Тестер не поднимает собственное прокси-ядро. Весь трафик проходит через тот sing-box,
которым управляет через его API-сервис.

## Запуск

```sh
python3 -m nodes_tester -c config/config.json
python3 -m nodes_tester --list-tests
python3 -m nodes_tester -c config/config.json --vacuum
```

На OpenWrt-пакете используются команды:

```sh
nodes-tester tester
nodes-tester tester --list-tests
nodes-tester vacuum
```

`VACUUM` блокирует обслуживание базы на время операции, поэтому его лучше запускать
редко и вне активного прогона.

## Выбор нод и порядок обхода

Runner читает участников selector из `testing_groups[0].selector.group`. Сейчас полноценно
используется первая testing group.

Leaf-нода должна иметь CRC в конце тега. Группы и записи без CRC пропускаются. Регион
определяется одним из способов:

- `region_groups.recognition: "parse"` — страна извлекается из имени ноды, затем сводится
  к `eu`, `us`, `ru` или `other`;
- `region_groups.recognition: "manually"` — регион берётся из явных списков.

Очередь строится с учётом хоста: ноды одного хоста раздвигаются, а `min_host_gap`
ограничивает частоту обращений к одному хосту с разными портами или протоколами. Это
снижает вероятность ограничений со стороны провайдера и ТСПУ.

## Проверки

| Тест | Что измеряет |
|---|---|
| `connectivity` | факт доступа в интернет, внешний IP, страну и colo |
| `latency` | TTFB |
| `jitter` | среднюю, минимальную и максимальную задержку, jitter и потери |
| `download` | скорость, устойчивость и признаки замедления |
| `reachability` | доступность набора целей |
| `heavy_download` | тяжёлую контрольную загрузку для лучших кандидатов |
| `gemini` | какой страной Google видит ноду и пускает ли её gemini.google.com |

Набор задаётся в `run.default.tests_enabled` и может переопределяться для testing group и
региона. `connectivity` служит GATE: его провал обнуляет итоговый балл. `heavy_download`
не входит в формулу рейтинга; свежий отрицательный результат временно запрещает выбор
кандидата. Его проходят ноды пула ротации перед сменой активной; нода с результатом моложе
`switching.rotation.interval` повторно не скачивает.

При `run.default.rotation_bound` проход запускается к сроку ротации группы и проверяет
только ноды групп, у которых этот срок наступил. Первый проход после старта и внеплановый
проход из админки проверяют все ноды. При `switching.rotation.align` (по умолчанию включён)
сроки ротации всех групп стоят на общей сетке с шагом `interval` и общим для слота `jitter`,
поэтому один проход обслуживает все группы. После переключения следующий срок — первый слот
не раньше `min_dwell`.

`gemini` — обязательный тест группы. Включается для групп нод через
`run.node_groups_specifics`, например для `ai`:

```json
"node_groups_specifics": [
  { "group": "ai", "default_overrides": { "required_tests": ["gemini"] } }
]
```

Тест открывает gemini.google.com `attempts` раз (по умолчанию 3) и берёт из страницы код
страны, которой Google определил клиента. Нода проходит, только если каждая попытка дала
HTTP 200 и страну вне `forbidden_countries` (по умолчанию RUS, BLR, CHN, HKG, MAC, IRN,
PRK, CUB, SYR). Одной попытки мало: часть нод выходит то по IPv4, то по IPv6 Cloudflare
WARP, и тогда Google видит то зарубежную страну, то Россию.

Тест гоняется отдельной фазой после основных проверок: для верхних `top_k` кандидатов группы
и её активной ноды, у которых нет свежего результата (`ttl_hours`, по умолчанию 6 ч), не
больше `max_per_pass` нод за проход. Провал выбивает ноду из пула, и проверяется
следующая. Активной в такой группе может быть только нода со свежим успешным результатом.
Если активная провалила тест или результат устарел, она заменяется; если не прошла ни одна
нода, `{group}-auto-out` переключается на `{group}-auto-out-failsafe`.

Сетевые тесты расходуют трафик. Размеры, URL и таймауты находятся в секции `tests`.

## Рейтинг

Рейтинг строится из нормированных факторов надёжности, устойчивости, замедления, jitter,
задержки и скорости. Затем применяются EWMA, доступность и штраф за колебания. Состояние
хранится в таблицах `scores` и `score_history`, а не в CSV.

Практические следствия:

- `score = 0` может означать провал GATE или отсутствие достаточных scoring-измерений;
- физические значения скорости и задержки нужно смотреть в `results`;
- старое измерение отдельного теста может относиться к другому проходу;
- изменение весов и порогов влияет на следующие обновления рейтинга.

Пороговые значения и веса задаются в `scoring`. Их актуальные дефолты находятся в
[`config.py`](config.py) и [`config/config.example.json`](../config/config.example.json).
Полная формула и правила интерпретации: [`SCORING.md`](SCORING.md).

## Переключение

Switcher использует рейтинг, ограничения и текущую активную ноду. Он поддерживает:

- аварийную замену недоступной ноды;
- замену по качеству после подтверждения несколькими циклами;
- периодическую ротацию среди лучших кандидатов;
- минимальное время удержания и cooldown;
- исключение недавно использованных кандидатов;
- дополнительную балансировку по провайдеру, стране, протоколу и трафику.

Автоматическое переключение меняет боевые selector в sing-box. Для первого знакомства его
можно отключить через `switching.enabled: false`.

## Монитор, пауза и карантин

Monitor следит за активными нодами между проходами. При наличии пользовательского трафика
он считает ноду живой. После периода тишины выполняет короткий SOCKS-зонд; несколько
провалов запускают аварийный выбор.

После провала GATE cooldown переводит ноду в паузу на растущее число проходов. После
достижения `max_skip` нода попадает в карантин на `garbage_hours`, затем получает одну
пробу. Успешный GATE снимает ограничение.

`cooldown.low_score` (по умолчанию 0 — выключено) отправляет в карантин и живые, но слабые
ноды: рейтинг ниже порога после не менее 3 замеров. Активные ноды не затрагиваются. После
карантина нода возвращается, если рейтинг по пробе поднялся до порога.

Ручные бан и карантин доступны через админку. Бан не удаляет ноду из подписки и не стирает
её историю.

## Хранение

При `storage.enabled: true` SQLite содержит:

- `nodes` и `endpoints` — текущий состав и сетевые адреса;
- `results` — сырые результаты проверок;
- `scores` и `score_history` — текущий рейтинг и история;
- `traffic` — агрегаты пользовательского трафика;
- `garbage` — паузы и карантин;
- `activations`, `switch_state`, `switch_recent`, `switch_activations` — состояние выбора;
- `node_events` — события жизненного цикла;
- `meta` — служебные значения, включая сквозной номер прохода.

Очистка по `retention_days` выполняется периодически. `VACUUM` вынесен в отдельную команду.
Не копируйте только `stats.db` из работающей WAL-базы: остановите процесс или используйте
SQLite backup.

Структура таблиц, очистка и резервное копирование описаны в [`STORAGE.md`](STORAGE.md).

## Тип выходного IP

После прохода выходные IP нод (`exit_ip` из `connectivity`), для которых нет свежих
сведений, проверяются одним пакетным запросом к ip-api.com через SOCKS тестера на лучшей
здоровой ноде — DNS-фильтры (NextDNS и блоклисты) часто блокируют ip-api.com на роутере; при
неудаче запрос идёт напрямую (`ip_info`: `enabled`, `url`, `ttl_days`, `timeout`, `via_tester`). Сведения — ASN, сеть, признаки
дата-центра, мобильной сети и известного прокси — кэшируются в таблице `ip_info` на
`ttl_days`. «Результаты» показывают тип IP (ДЦ, домашний, мобильный) и расхождение страны
по базе со страной по Cloudflare. На выбор нод тип IP пока не влияет.

## Уведомления

`notify` отправляет сообщения в Telegram (`telegram.token`, `telegram.chat_id`) и/или
webhook (`webhook.url`, POST JSON `{event, text, ts}`). Собственный трафик роутера часто
идёт мимо прокси, и Telegram напрямую недоступен: если отправка не прошла, она повторяется
через SOCKS тестера на лучшей здоровой ноде (`via_tester`, по умолчанию включено); `proxy`
задаёт свой прокси. События (`events`):

| Событие | Когда |
|---|---|
| `switch` | переключение ноды с причиной из `switch_reasons` (по умолчанию `emergency`, `emergency-stuck`) |
| `failsafe` | группа ушла на `{group}-auto-out-failsafe` |
| `rollback` | новый конфиг sing-box не дал связности и был возвращён прежний |
| `pipeline` | прогон конвейера завершился ошибкой или тайм-аутом |
| `subscription` | подписка не загрузилась; сообщается, сколько часов осталось до потери прошлых нод |
| `expiry` | до конца подписки ≤ `expiry_days` дней или израсходовано ≥ 90 % трафика (раз в сутки) |
| `singbox` | sing-box остановлен или запущен из админки, переключён killswitch, sing-box не работает дольше `singbox_control.down_alert` |

Отправка идёт фоновым потоком; повтор того же события подавляется на `dedupe_minutes`, общий
предел — `max_per_hour`. Кнопка «Отправить тестовое сообщение» в «Настройках» использует
настройки работающего процесса.

## sing-box: остановка и killswitch

`singbox_control` (только OpenWrt) даёт админке аварийную остановку и запуск sing-box. В режиме
TUN sing-box при остановке сам снимает маршруты. Пока стоит флаг остановки (`stop_flag`, tmpfs),
`apply-nodes.sh` не применяет конфиг; перезагрузка роутера флаг сбрасывает и запускает sing-box.

Killswitch — отдельная служба роутера (`killswitch_init`, по умолчанию `/etc/init.d/killswitch`),
которая с загрузки держит постоянную таблицу nftables (`killswitch_table`) и не выпускает LAN в
интернет мимо sing-box. Правила задаются в самой службе; nodes-tester их не создаёт, а только
показывает, загружена ли таблица и сколько пакетов отбито, и включает или выключает службу
(`start` + `enable`, `stop` + `disable`). Если службы нет, переключатель не показывается.

## Встроенная админка

При `dashboard.enabled: true` HTTP-сервер запускается внутри Runner и получает доступ к
живому статусу, журналу и действиям. Отдельный `python3 -m dashboard` работает без Runner:
он читает базу и файлы, но не может запустить проход или выполнить живое переключение.

Пользовательское руководство: [`docs/USAGE.md`](../docs/USAGE.md). Техническое описание:
[`dashboard/README.md`](../dashboard/README.md).
