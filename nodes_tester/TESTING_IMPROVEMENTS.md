# Рекомендации по улучшению тестирования нод

Дата повторной проверки: 2026-08-31

Статус документа: предложения для обсуждения, без изменений реализации.

## Резюме

Текущий набор runtime-тестов покрывает основные характеристики ноды:

- доступ в интернет и определение выходного IP;
- HTTP TTFB;
- разброс и долю неудачных HTTP-запросов;
- скорость, удержание и замедление потоковой загрузки;
- доступность набора внешних сервисов.

Первый шаг к многоступенчатой стратегии уже реализован: пять лёгких тестов проходят все ноды, затем отдельный `heavy_download` запускается для лучших кандидатов региона и активной ноды. Следующий шаг — сделать быстрый gate стадийным, корректно учитывать пропущенные измерения и уменьшить зависимость рейтинга от одного внешнего измерительного сервиса.

## Текущая механика

Runner строит host-aware порядок нод, выдерживает `min_host_gap` для одного endpoint и после переключения selector на очередную ноду:

1. Ожидает `switch_delay` (сейчас 1 секунда).
2. Создаёт одну SOCKS5-сессию.
3. Последовательно запускает тесты в порядке `tests_enabled`.
4. Записывает результаты в report/SQLite.
5. Вычисляет gate и score.
6. При провале gate обновляет cooldown и при необходимости инициирует боевое переключение.
7. После лёгкой фазы выбирает top-`heavy_candidates` по регионам плюс активные ноды и запускает для них `heavy_download` как veto.

Сейчас зарегистрировано шесть runtime-тестов: пять тестов лёгкой фазы и один тест второй фазы:

1. `connectivity`.
2. `latency`.
3. `jitter`.
4. `download`.
5. `reachability`.
6. `heavy_download` — отдельная тяжёлая проверка кандидатов, не входящая непосредственно в score.

Отдельный `stability` удалён. Его показатели объединены с `download`, поэтому скорость, удержание передачи и троттлинг вычисляются по одной загрузке.

## Анализ существующих тестов

### `connectivity`

Тест отправляет HTTP-запрос через ноду и нормализует ответ внешнего сервиса:

- Cloudflare trace используется по умолчанию;
- `curlmyip.ru/geo` используется для RU;
- сохраняются `exit_ip`, `country`, а при наличии — `colo`, ASN и организация.

Сетевой или HTTP-сбой даёт `ok=false`. Однако HTTP 200 считается успехом даже при нераспознанном теле. Страница-заглушка, перехват или изменение формата ответа могут дать `ok=true` без подтверждённого выходного IP.

Рекомендации:

- требовать корректный публичный `exit_ip` для полного успеха;
- отделить `transport_ok` от `identity_verified`;
- валидировать формат ответа выбранного сервиса;
- отмечать несовпадение наблюдаемой страны с маркировкой ноды как anomaly;
- проверять, что после переключения selector действительно изменился ожидаемый маршрут;
- использовать кворум минимум из двух независимых connectivity-сервисов для hard gate.

### `latency`

Измеряется время от начала HTTP-запроса до первого фрагмента тела — TTFB.

Это не чистый сетевой RTT. В результат могут входить:

- установка SOCKS/TCP-соединения;
- TLS handshake;
- время обработки запроса сервером;
- HTTP и сетевые задержки.

Рекомендации:

- явно называть показатель `http_ttfb_ms`;
- разделить cold и warm измерения;
- для cold TTFB создавать новое соединение;
- для warm TTFB использовать установленное соединение;
- хранить median и p90/p95, а не только одно значение;
- использовать минимум два независимых endpoint на регион.

### `jitter`

Тест выполняет несколько HTTP TTFB-запросов, сейчас пять, и вычисляет:

- среднее, минимум и максимум;
- standard deviation как `jitter_ms`;
- долю неудачных запросов как `loss_pct`.

Фактически это разброс HTTP TTFB, а не сетевой jitter. `loss_pct` является долей неудачных HTTP-запросов, а не потерей IP-пакетов. Запросы используют одну `requests.Session` и могут переиспользовать соединение, поэтому samples не полностью независимы.

Рекомендации:

- переименовать метрики в `ttfb_jitter_ms` и `request_failure_pct`;
- увеличить стандартный объём до 8–12 samples;
- использовать median, p90/p95 и MAD или другой robust spread;
- добавить режим независимых fresh connections;
- отдельно хранить cold и warm статистику;
- не интерпретировать HTTP failures как packet loss.

### `download`

Одна потоковая загрузка вычисляет:

- `speed_mbps` — среднюю скорость;
- `hold_ratio` — долю скачанного от `Content-Length`;
- `throttle_ratio` — отношение скорости последнего байтового окна к первому;
- признаки transport break и server limit.

Объединение прежних `download` и `stability` — полезное решение: уменьшается трафик и число запросов к speed endpoint. Но текущий тест не гарантирует проверку в течение заданных 20 секунд. Быстрая нода скачивает файл полностью за короткое время, а медленная может упереться в `duration` и получить fail, хотя соединение было стабильным.

Первое окно также искажено TCP slow start. Сравнение первого и последнего окна может показывать ускорение или скрывать поздний throttle, не связанный с блокировкой.

Кроме того, любой `HTTPError`, включая 401/403/404, сейчас классифицируется как `server_limit` и `ok=true`, хотя такой статус может означать ошибочный URL или реальную блокировку.

Рекомендации:

- разделить результаты на `transport_ok`, `throughput_ok` и `completed`;
- не считать низкую скорость автоматически транспортной нестабильностью;
- использовать файл/поток, который гарантированно больше объёма, передаваемого за `duration`;
- считать штатное достижение `duration` успешным завершением sustained-теста;
- отличать 429, ожидаемые 5xx, 401/403/404 и proxy-generated errors;
- пропускать начальное окно TCP slow start;
- разбивать передачу на несколько окон и сравнивать медианы ранней и поздней стабильной части;
- хранить временной профиль скорости или хотя бы p25/p50/p75;
- сохранить текущий запуск тяжёлой загрузки только для кандидатов, но сделать TTL и fallback-политику veto явными.

### `reachability`

Тест параллельно обращается к набору внешних целей. Любой HTTP-статус меньше 500 считается доступностью, а общий `ok=true` устанавливается, если ответила хотя бы одна цель.

Такой подход показывает, что соединение/TLS/HTTP в какой-то форме работает, но не гарантирует прикладную работоспособность сервиса. Статусы 403, 404, 429 и redirects также считаются успешной доступностью.

Рекомендации:

- разделить транспортную и прикладную доступность;
- для каждой цели задавать допустимые статусы, ожидаемое тело, правила redirect, вес и критичность;
- группировать цели по категориям: neutral, search, video, messaging, social и critical;
- строить hard gate по кворуму независимых neutral endpoint;
- не делать отдельную развлекательную или социальную цель hard gate;
- сохранять latency и тип ошибки для каждой цели;
- использовать отдельные sessions или явно изолированный пул вместо общей mutable session во worker-потоках.

## Проблемы текущего orchestration

### Все тесты запускаются даже после очевидного провала

Если `connectivity` не прошёл, runner всё равно запускает latency, jitter, download и reachability. Это расходует трафик и задерживает прогон мёртвых нод.

Рекомендуемая механика:

1. Выполнить быстрый connectivity quorum.
2. При полном провале повторить через независимый endpoint.
3. Если подтверждён hard fail — прекратить тестирование ноды.
4. Если причина неоднозначна — выполнить короткую диагностическую ветку без тяжёлого download.

### Сильная зависимость от одного измерительного провайдера

Для большинства регионов connectivity, latency, jitter и download зависят от Cloudflare. Для RU значительная часть измерений зависит от Selectel и curlmyip. Сбой или rate limit конкретного сервиса может выглядеть как одновременная деградация всех нод.

Рекомендации:

- минимум два независимых connectivity endpoint;
- минимум два latency/download endpoint на регион;
- контрольная проверка самих endpoint;
- детектор коррелированного массового сбоя;
- не выполнять emergency switching, если одновременно деградировало большинство нод и есть признаки отказа измерительной инфраструктуры.

### Временной bias

Ноды тестируются последовательно в host-aware порядке. Изменение нагрузки speed endpoint или качества сети со временем всё равно может дать преимущество нодам, протестированным раньше или позже.

Рекомендации:

- ротировать или перемешивать порядок нод между прогонами;
- сохранять детерминированный seed/порядок в отчёте;
- периодически тестировать контрольную ноду между группами;
- не сравнивать измерения, полученные с разных endpoint, без отдельной нормализации.

### Изоляция ошибок

Неожиданное исключение внутри конкретного теста может прервать обработку ноды, а session закрывается не через `finally`.

Рекомендации:

- изолировать каждый `test.run()`;
- превращать ожидаемые программные/сетевые ошибки в структурированный `TestResult`;
- гарантированно закрывать session через context manager или `finally`;
- различать `test_failed` и `test_infrastructure_error`.

## Рекомендуемая многоступенчатая стратегия

| Уровень | Состав | Частота |
|---|---|---|
| Fast | connectivity quorum, exit IP, 2–3 fresh connections | каждый прогон |
| Standard | cold/warm latency, HTTP failure rate, critical reachability | каждые 2–3 прогона |
| Heavy | sustained download 20–30 сек., throttle profile, upload | каждые 5–10 прогонов или для кандидатов |
| Protocol | DNS, UDP, QUIC, IPv4/IPv6 | периодически |
| Diagnostic | полная app matrix, idle connection, censorship fingerprint | вручную или при аномалии |

Механизм `every` уже поддерживается базовым классом, а тяжёлая фаза кандидатов реализована в runner. При этом полностью пропущенный через `every` набор сейчас превращается в пустой результат с `gate=true` и score 0. До расширения scheduler нужен отдельный исход `not_measured`, coverage/TTL предыдущих метрик и явная политика для новых нод.

## Новые тесты

### Поведение DNS-разрешения

Проверять:

- возможность резолвинга через туннель;
- фактически используемый resolver;
- фактический путь DNS-разрешения;
- NXDOMAIN;
- A/AAAA;
- крупные ответы и TCP fallback.

Предпочтителен контролируемый домен со случайными поддоменами, позволяющий сопоставить DNS-запрос и последующее HTTP-соединение.

### Fresh-connection reliability

Выполнять несколько независимых подключений с новыми sessions.

Предлагаемые метрики:

- `connect_success_pct`;
- median/p95 cold TTFB;
- число DNS/connect/TLS/timeout/reset ошибок;
- доля успешных TLS handshakes.

Эта метрика лучше характеризует способность открывать новые соединения, чем текущий условный `loss_pct`.

### UDP и QUIC

Текущие тесты через `requests` проверяют только TCP/HTTP. Отдельно следует тестировать UDP, если ноды используются для:

- DNS по UDP;
- HTTP/3 и QUIC;
- видеозвонков;
- игр;
- UDP-native proxy protocols.

Для этого потребуется SOCKS5 UDP ASSOCIATE либо специализированный тестовый клиент.

### Upload

Небольшой upload test нужен для двусторонних сценариев. Желательно измерять:

- среднюю скорость;
- успешность передачи заданного объёма;
- транспортные resets/timeouts;
- стабильность нескольких временных окон.

Запускать редко и только на контролируемый endpoint.

### Idle/long-lived connection

Активная загрузка не обнаруживает разрыв простаивающих соединений. Тест должен:

1. Установить TCP/TLS/WebSocket-соединение.
2. Оставить его без трафика на заданное время.
3. Отправить ping или данные.
4. Проверить, осталось ли соединение живым.

Это важно для SSH, WebSocket, мессенджеров и long polling.

### IPv4/IPv6

Отдельно проверять:

- IPv4 egress;
- IPv6 egress;
- dual-stack resolution;
- доступность IPv6-only endpoint;
- фактическое семейство выходного адреса.

### Controlled censorship fingerprint

Для диагностики фильтрации полезен собственный endpoint, позволяющий сравнивать:

- одинаковый IP с разными SNI/Host;
- HTTP и HTTPS;
- различные размеры и паттерны передачи;
- TCP и QUIC;
- непрерывную передачу и передачу с паузами.

Так можно отличить плохую ноду от фильтрации конкретного домена, SNI или транспортного профиля.

## Изменения рейтинга

Сейчас отсутствующие компоненты исключаются, а веса оставшихся компонентов перенормируются. Поэтому score с полным набором тестов и score с одним-двумя тестами формально попадают на одну шкалу 0–100, хотя имеют разную доказательную силу.

Рекомендации:

- хранить отдельные `score_fast`, `score_transport` и `score_apps`;
- добавить `coverage` или `confidence`;
- определить минимальный набор свежих тестов для production activation;
- сохранять последнее значение тяжёлого теста с TTL, а не исключать компонент в каждом пропущенном прогоне;
- помечать устаревшие компоненты;
- строить hard gate по кворуму независимых быстрых тестов;
- отличать `node failure` от `measurement infrastructure failure`;
- не сравнивать напрямую score, полученные с разным coverage;
- не инициировать автоматическое переключение на основе единственного внешнего endpoint.

## Предлагаемые метрики результата

Для наблюдаемости полезно унифицировать результат каждого теста:

```text
ok                       итог теста
failure_domain           node | endpoint | tester | config | unknown
failure_stage            dns | socks | connect | tls | http | stream | validation
endpoint                 использованный endpoint
duration_ms              длительность теста
attempts                  число попыток
fresh_connection         использовалось ли новое соединение
measured_at              время измерения
valid_until               TTL метрики
```

Это позволит рейтингу принимать решения не только по `ok`, но и по происхождению сбоя.

## Приоритет внедрения

### P1 — максимальный эффект

1. Connectivity quorum из независимых endpoint.
2. Настоящий sustained-download заданной длительности.
3. Корректная классификация HTTP-ошибок download.
4. Fresh-connection reliability.
5. Разделение `request_failure_pct` и настоящего packet/transport loss.
6. Short-circuit тяжёлых тестов после подтверждённого hard fail.

### P2 — качество рейтинга

1. Coverage/confidence и TTL тяжёлых метрик.
2. Раздельные fast/transport/apps scores.
3. Robust latency statistics.
4. Категории и ожидаемые ответы reachability.
5. Детектор массового сбоя тестовой инфраструктуры.

### P3 — расширение покрытия

1. Поведение DNS-разрешения.
2. UDP/QUIC.
3. IPv4/IPv6.
4. Upload.
5. Idle connection.
6. Controlled censorship fingerprint.

## Целевая последовательность тестирования ноды

```text
selector switch
    ↓
route/exit-IP confirmation
    ↓
connectivity quorum
    ├── hard fail подтверждён → записать причину, cooldown, остановить тесты ноды
    └── success/ambiguous
            ↓
fresh-connection reliability + cold/warm latency
            ↓
critical reachability
            ↓
нода новая / кандидат / heavy test due?
    ├── нет → score с coverage и TTL предыдущих тяжёлых метрик
    └── да  → sustained download + protocol/application tests
```

Такая схема уменьшит объём трафика, ускорит обработку мёртвых нод и сделает автоматическое переключение менее зависимым от временных проблем одного измерительного сервиса.
