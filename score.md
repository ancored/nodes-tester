# Система рейтингования нод (scoring)

Документ описывает, как из результатов тестов получается итоговый рейтинг ноды
`score` ∈ [0, 100], который затем использует переключатель (`switcher.py`).
Все формулы соответствуют коду `nodes_tester/scoring.py`, а параметры — секции
`scoring` в `config.yaml`.

---

## 1. Философия

Рейтинг заточен под условия РФ (ТСПУ/DPI), где **стабильность важнее пиковой
скорости**. Поэтому:

- ~80% веса отдано стабильности (надёжность, ровность, устойчивость к
  замедлению и обрывам), ~20% — сырой производительности (латентность, скорость);
- **жёсткие условия (GATE)** — если нода прямо сейчас недоступна, рейтинг = 0
  немедленно, без сглаживания;
- решение принимается не по одному прогону, а по **истории** (EWMA + штраф за
  нестабильность + учёт доступности).

---

## 2. Конвейер

```
тесты ноды ──► нормализация метрик [0..1] ──► взвешенная сумма ──► S_run (0..100, за прогон)
                                                     │ (GATE: провал → 0)
                                                     ▼
                              EWMA по прогонам + flap-penalty + avail-factor
                                                     │ (GATE-провал этого прогона → 0)
                                                     ▼
                                              S_final (score в score.csv)
```

- **S_run** — мгновенный балл за один прогон.
- **S_final** — сглаженный по истории рейтинг; именно он лежит в `score.csv`
  и используется для переключения.

---

## 3. Тесты → сырые метрики

| Тест           | Метрики, идущие в рейтинг                                   |
|----------------|------------------------------------------------------------|
| `connectivity` | `ok` (есть ли выход) — для GATE                             |
| `latency`      | `ttfb_ms`                                                  |
| `jitter`       | `jitter_ms`, `avg_ms`, `loss_pct`                          |
| `download`     | `speed_mbps`                                               |
| `stability`    | `survive_seconds`, `target`, `throttle_ratio`             |
| `reachability` | `reached`, `total`                                        |

Отсутствующий тест (выключен или пропущен по `every`) просто исключается из
расчёта — веса пере-нормируются по присутствующим компонентам.

---

## 4. Нормализация метрик

Две базовые функции переводят сырую метрику в [0, 1]:

```text
clamp01(x)              = min(max(x, 0), 1)

lower_better(x, g, b)   = clamp01( (b - x) / (b - g) )     # меньше = лучше
higher_better(x, lo, hi)= clamp01( (x - lo) / (hi - lo) )  # больше = лучше
```

- `g` (good) — значение, при котором под-скор = 1; `b` (bad) — при котором = 0.
- Для `higher_better`: `lo` даёт 0, `hi` (target) даёт 1 (и выше — тоже 1, т.е.
  «потолок»: сверхбыстрая нода не получает преимущества над «достаточно быстрой»).

### Пороги (секция `scoring.thresholds`)

| Порог           | Значение | Куда идёт                                    |
|-----------------|----------|----------------------------------------------|
| `ttfb_good`     | 150      | latency: good                                |
| `ttfb_bad`      | 1500     | latency: bad                                 |
| `jitter_good`   | 15       | jitter: good                                 |
| `jitter_bad`    | 250      | jitter: bad                                  |
| `loss_gate`     | 50       | GATE: loss% выше → провал                     |
| `dl_min`        | 2        | throughput: lo                               |
| `dl_target`     | 25       | throughput: hi (потолок)                     |
| `throttle_bad`  | 0.3      | throttle: lo                                 |
| `throttle_good` | 0.9      | throttle: hi                                 |
| `hold_min`      | 5        | reliability(hold): lo                        |
| `hold_target`   | 20       | reliability(hold): hi (если не задан target) |
| `cv_good`       | 0.1      | consistency: good                            |
| `cv_bad`        | 0.8      | consistency: bad                             |

---

## 5. Компоненты рейтинга (под-скоры [0..1])

Каждый компонент считается из метрик последнего прогона. Если исходного теста
нет — компонент отсутствует.

### 5.1. latency
```text
latency = lower_better(ttfb_ms, ttfb_good, ttfb_bad)      если latency.ok
        = 0                                               если latency провален
```

### 5.2. jitter
```text
jitter = lower_better(jitter_ms, jitter_good, jitter_bad) если jitter.ok
       = 0                                                если jitter провален
```

### 5.3. consistency (ровность латентности)
Коэффициент вариации `CV = jitter_ms / avg_ms` — насколько «скачет» латентность:
```text
consistency = lower_better(CV, cv_good, cv_bad)           если jitter.ok и avg_ms>0
            = 0                                            если jitter провален
```

### 5.4. throughput (скорость, с потолком)
```text
throughput = higher_better(speed_mbps, dl_min, dl_target) если download.ok
           = 0                                             если download провален
```

### 5.5. throttle (устойчивость к замедлению)
Из `stability.throttle_ratio` (скорость последнего окна / первого):
```text
throttle = higher_better(throttle_ratio, throttle_bad, throttle_good)  если ratio есть
         = 0                                                            если stability провален без ratio
```

### 5.6. reliability (надёжность) — ключевой компонент
Комбинация трёх сигналов (берутся те, что доступны, веса пере-нормируются):

```text
rel_req  = clamp01(1 - loss_pct/100)                       # доля успешных запросов (jitter)
rel_hold = higher_better(survive_seconds, hold_min, target)# выживаемость соединения (stability)
reach    = reached / total                                 # доля доступных целей (reachability)

reliability = (0.5·rel_req + 0.3·rel_hold + 0.2·reach) / (сумма весов присутствующих)
```
`target` = `stability.target` (обычно = `duration`) или `hold_target`.

---

## 6. GATE (жёсткие условия провала)

`gate = False`, если выполнено ЛЮБОЕ:

1. `connectivity` присутствует и `ok == false` (нет выхода в интернет);
2. `jitter.loss_pct > loss_gate` (напр. > 50%);
3. `reachability` присутствует, `total > 0`, но `reached == 0` (всё недоступно);
4. среди всех тестов есть флаги `ok`, и **ни один** не `true` (всё провалено).

Иначе `gate = True`.

---

## 7. Мгновенный балл S_run (за один прогон)

```text
если gate == False:
    S_run = 0
иначе:
    S_run = 100 · ( Σ wᵢ·compᵢ ) / ( Σ wᵢ по присутствующим compᵢ )
```

### Веса (секция `scoring.weights`)

| Компонент     | Вес  | Отражает                        |
|---------------|------|---------------------------------|
| reliability   | 0.35 | доходит и держится ли           |
| consistency   | 0.20 | ровно или скачет                |
| throttle      | 0.15 | не режут ли скорость со временем |
| jitter        | 0.10 | микро-стабильность              |
| latency       | 0.10 | отзывчивость                    |
| throughput    | 0.10 | сырая скорость                  |

Стабильность (первые 4) ≈ **0.80**, производительность ≈ 0.20. Знаменатель —
сумма весов только тех компонентов, что реально посчитаны в этом прогоне.

---

## 8. Временнáя агрегация (EWMA)

Состояние ноды между прогонами: `score_ewma`, `flap`, `avail`, `samples`
(хранится в `score.csv`). Параметр `α = scoring.alpha` (0.3).

Первый прогон ноды:
```text
score_ewma = S_run
flap       = 0
avail      = gate ? 1 : 0
samples    = 1
```

Каждый следующий прогон (`g = gate ? 1 : 0`):
```text
score_ewma = α·S_run + (1-α)·score_ewma_prev
flap       = α·|S_run - score_ewma_prev| + (1-α)·flap_prev
avail      = α·g + (1-α)·avail_prev
samples    = samples_prev + 1
```

- **score_ewma** — сглаженная «база» рейтинга.
- **flap** — сглаженная величина рывков рейтинга: чем сильнее нода «прыгает»
  от прогона к прогону, тем больше штраф.
- **avail** — сглаженная доступность (доля прогонов, прошедших GATE).

### Множитель доступности
```text
avail_full  = scoring.avail_full  (0.9)
avail_floor = scoring.avail_floor (0.7)

if avail >= avail_full:   avail_factor = 1.0
elif avail <= avail_floor: avail_factor = 0.5
else: avail_factor = 0.5 + 0.5·(avail - avail_floor)/(avail_full - avail_floor)
```
Нода, часто падающая GATE, получает `avail_factor` вплоть до 0.5 — её сглаженный
рейтинг режется вдвое, даже если в удачные прогоны она быстрая.

---

## 9. Итоговый рейтинг S_final

```text
если gate этого прогона == False:
    S_final = 0                       # обнуление сразу, без сглаживания
иначе:
    S_final = clamp( score_ewma · avail_factor − flap_lambda · flap , 0, 100 )
```
`flap_lambda = scoring.flap_lambda` (0.5).

**Обнуление при провале.** Ключевое правило: если нода провалила GATE в текущем
прогоне (заблокирована/недоступна прямо сейчас) — `S_final = 0` немедленно.
EWMA-состояние при этом продолжает копиться внутри (для ранжирования живых нод и
штрафа за флаппинг при восстановлении), но отображаемый и используемый рейтинг —
ноль. Это же мгновенно исключает ноду из кандидатов на переключение.

## 10. Разобранный пример (3 прогона)

Нода EU, пороги/веса по умолчанию.

**Прогон 1 — всё отлично:** ttfb=120, jitter=10 (avg=130), dl=30, throttle=0.9,
survive=20, reach=15/15, loss=0.
Все компоненты ≈ 1 → `S_run = 100`, gate=True.
Первый прогон: `score_ewma=100, flap=0, avail=1, samples=1`.
`avail_factor=1.0` → `S_final = 100·1 − 0.5·0 = 100`.

**Прогон 2 — нода заблокирована:** `connectivity.ok=false` → gate=False → `S_run=0`.
```text
score_ewma = 0.3·0 + 0.7·100 = 70
flap       = 0.3·|0-100| + 0.7·0 = 30
avail      = 0.3·0 + 0.7·1 = 0.7
avail_factor(0.7) = 0.5
S_final    = 0   (т.к. gate этого прогона == False — обнуление)
```
В `score.csv` рейтинг = **0**, нода выбывает из кандидатов; если была активной —
срабатывает EMERGENCY-переключение.

**Прогон 3 — нода восстановилась:** снова `S_run=100`, gate=True.
```text
score_ewma = 0.3·100 + 0.7·70 = 79
flap       = 0.3·|100-70| + 0.7·30 = 9 + 21 = 30
avail      = 0.3·1 + 0.7·0.7 = 0.79
avail_factor(0.79) = 0.5 + 0.5·(0.79-0.7)/0.2 = 0.725
S_final    = clamp(79·0.725 − 0.5·30) = clamp(57.3 − 15) = 42.3
```
Восстановившаяся нода сидит на ~**42**, а не сразу 100 — наказана за недавний
флаппинг и просевшую доступность. Через несколько стабильных прогонов рейтинг
снова подрастёт к 100.

## 11. Файл рейтинга `score.csv`

Одна строка на ноду; активные сверху, далее по убыванию `score`.

| Колонка                                              | Смысл                                  |
|------------------------------------------------------|----------------------------------------|
| `node, provider, protocol, region, country, id`      | идентичность ноды                      |
| `active`                                             | 1 — активная в проде (её выбрал switcher)|
| `score`                                              | **S_final [0..100]** — итог            |
| `reliability, consistency, throttle, jitter, latency, throughput` | под-скоры последнего прогона [0..1] (наблюдаемость) |
| `score_ewma, avail, flap, samples`                   | EWMA-состояние (для продолжения)       |
| `last_seen`                                          | номер прогона, где ноду видели         |

Исчезнувшие из Clash API ноды удаляются из файла в конце прогона.

---

## 12. Как рейтинг используется при переключении

`switcher.py` (см. README) на регион:

- **кандидаты** = ноды региона с `score > 0` (провалившие GATE — с рейтингом 0 —
  автоматически исключены);
- **EMERGENCY** — по мгновенному провалу GATE активной ноды (не по S_final);
- **QUALITY** — кандидат должен превзойти активную по `score` на `quality_margin`
  устойчиво `confirm_cycles` прогонов;
- **ROTATION** — среди нод с `score ≥ rotation.min_score`.

---

## 13. Тюнинг

- Хочешь **жёстче наказывать флаппинг** — подними `flap_lambda`.
- Хочешь **быстрее реагировать** на свежие прогоны — подними `alpha` (меньше
  сглаживания); медленнее и стабильнее — понизь.
- Считаешь, что **скорость важнее** — перераспредели `weights` в пользу
  `throughput`/`latency` (сумма не обязана быть 1: знаменатель нормирует).
- Строже к нестабильным по доступности нодам — подними `avail_floor`/`avail_full`.
- Границы «хорошо/плохо» метрик — в `thresholds` (напр. под медленный канал
  понизь `dl_target`).

Все параметры — в секции `scoring` конфига; менять можно без правки кода.
