# Рейтинг прокси-нод

Этот документ описывает текущую модель рейтинга из `nodes_tester/scoring.py`. Результат хранится в таблице `scores` базы `stats.db`; история по прогонам - в `score_history`.

## Коротко

Рейтинг оценивает доступность и стабильность ноды по шкале от 0 до 100. Скорость влияет на результат меньше, чем надёжность соединения.

Расчёт проходит в три шага:

1. Метрики последнего прогона переводятся в подоценки от 0 до 1.
2. Из доступных подоценок получается мгновенный балл `S_run`.
3. История сглаживается через EWMA. Провал GATE всё равно сразу обнуляет итоговый `score`.

```text
результаты тестов -> подоценки -> S_run -> EWMA и штрафы -> score
                         |
                         +-> провал GATE -> score = 0
```

`Scoreboard` записывает снимок рейтинга после каждого прогона. Переключатель использует этот снимок для выбора кандидатов.

## Какие тесты участвуют

| Тест | Метрики для рейтинга |
|---|---|
| `connectivity` | `ok`; участвует в GATE |
| `latency` | `ttfb_ms` |
| `jitter` | `jitter_ms`, `avg_ms`, `loss_pct` |
| `download` | `speed_mbps`, `throttle_ratio`, `hold_ratio`, `limited`, `http_error` |
| `reachability` | `reached`, `total` |

Отдельного теста `stability` больше нет. Его показатели `throttle_ratio` и `hold_ratio` считает `download` в рамках одной загрузки.

`heavy_download` работает отдельно. Он проверяет лучших кандидатов и активную ноду, затем сохраняет `heavy_ok` и `heavy_ts`. В формулу рейтинга этот тест не входит: свежий отрицательный результат служит veto при выборе кандидатов.

Если тест отключён или не запускался, его компоненты не участвуют в расчёте. Веса оставшихся компонентов перенормируются.

## Нормализация метрик

Две функции переводят метрику в диапазон от 0 до 1:

```text
clamp01(x)                 = min(max(x, 0), 1)
lower_better(x, good, bad) = clamp01((bad - x) / (bad - good))
higher_better(x, lo, hi)   = clamp01((x - lo) / (hi - lo))
```

`lower_better` применяют там, где меньшее значение лучше: задержка, jitter и коэффициент вариации. `higher_better` используют для скорости и устойчивости загрузки.

### Пороговые значения

Значения ниже взяты из `scoring.thresholds` в `config/config.example.json`.

| Параметр | По умолчанию | Назначение |
|---|---:|---|
| `ttfb_good` | 150 | TTFB с подоценкой 1 |
| `ttfb_bad` | 1500 | TTFB с подоценкой 0 |
| `jitter_good` | 15 | jitter с подоценкой 1 |
| `jitter_bad` | 250 | jitter с подоценкой 0 |
| `loss_gate` | 50 | предел `loss_pct` для GATE |
| `dl_min` | 2 | скорость с подоценкой 0 |
| `dl_target` | 25 | скорость с подоценкой 1 |
| `throttle_bad` | 0.3 | `throttle_ratio` с подоценкой 0 |
| `throttle_good` | 0.9 | `throttle_ratio` с подоценкой 1 |
| `cv_good` | 0.1 | коэффициент вариации с подоценкой 1 |
| `cv_bad` | 0.8 | коэффициент вариации с подоценкой 0 |

`hold_min` и `hold_target` остались в схеме конфигурации для совместимости. Текущий код использует готовый `download.hold_ratio`, ограниченный диапазоном от 0 до 1.

## Компоненты рейтинга

### Задержка

```text
latency = lower_better(ttfb_ms, ttfb_good, ttfb_bad), если latency.ok
latency = 0, если тест завершился ошибкой
```

### Jitter

```text
jitter = lower_better(jitter_ms, jitter_good, jitter_bad), если jitter.ok
jitter = 0, если тест завершился ошибкой
```

### Ровность задержки

Коэффициент вариации показывает разброс относительно средней задержки:

```text
CV = jitter_ms / avg_ms
consistency = lower_better(CV, cv_good, cv_bad)
```

Компонент рассчитывается, если `jitter.ok`, `avg_ms` больше нуля и `jitter_ms` присутствует. При ошибке jitter-теста значение равно 0.

### Скорость

```text
throughput = higher_better(speed_mbps, dl_min, dl_target)
```

Скорость выше `dl_target` не даёт дополнительного преимущества. Если транспортная загрузка завершилась ошибкой, компонент равен 0.

Ответ измерительного сервера с `limited=true` или `http_error=true` считается нейтральным: скорость и удержание не оцениваются, потому что такой ответ сам по себе не доказывает проблему ноды.

### Устойчивость к замедлению

```text
throttle = higher_better(throttle_ratio, throttle_bad, throttle_good)
```

`throttle_ratio` сравнивает скорость последнего и первого байтовых окон одной загрузки. При транспортной ошибке без нейтрального ответа компонент равен 0.

### Надёжность

Компонент собирается из доступных сигналов:

```text
rel_req  = clamp01(1 - loss_pct / 100)
rel_hold = clamp01(hold_ratio)
reach    = reached / total

reliability = weighted_mean(
    rel_req  с весом 0.5,
    rel_hold с весом 0.3,
    reach    с весом 0.2
)
```

Если части данных нет, знаменатель включает только присутствующие сигналы.

## GATE

GATE отвечает на вопрос, можно ли считать ноду доступной в этом прогоне. Он провален, если выполняется хотя бы одно условие:

1. `connectivity` присутствует и вернул `ok=false`.
2. `jitter.loss_pct` выше `loss_gate`.
3. `reachability.total` больше нуля, а `reached` равен нулю.
4. В результатах есть флаги `ok`, но ни один тест не завершился успешно.

При провале GATE `S_run` и итоговый `score` равны 0.

## Мгновенный балл

```text
S_run = 100 * sum(weight_i * component_i) / sum(weight_i)
```

В сумму входят только рассчитанные компоненты.

| Компонент | Вес |
|---|---:|
| `reliability` | 0.35 |
| `consistency` | 0.20 |
| `throttle` | 0.15 |
| `jitter` | 0.10 |
| `latency` | 0.10 |
| `throughput` | 0.10 |

Первые четыре компонента дают 80 процентов общего веса. Задержка и скорость вместе дают 20 процентов.

## Сглаживание между прогонами

Для каждой ноды таблица `scores` хранит `score_ewma`, `flap`, `avail` и `samples`. По умолчанию `alpha` равна 0.3.

Первый прогон:

```text
score_ewma = S_run
flap       = 0
avail      = 1 при успешном GATE, иначе 0
samples    = 1
```

Следующие прогоны:

```text
g          = 1 при успешном GATE, иначе 0
score_ewma = alpha * S_run + (1 - alpha) * previous_score_ewma
flap       = alpha * abs(S_run - previous_score_ewma) + (1 - alpha) * previous_flap
avail      = alpha * g + (1 - alpha) * previous_avail
samples    = previous_samples + 1
```

`score_ewma` сглаживает результат, `flap` измеряет резкие изменения, `avail` отражает недавнюю доступность.

### Множитель доступности

По умолчанию `avail_floor` равен 0.7, а `avail_full` равен 0.9.

```text
если avail >= avail_full:
    avail_factor = 1.0
если avail <= avail_floor:
    avail_factor = 0.5
иначе:
    avail_factor = 0.5 + 0.5 * (avail - avail_floor) / (avail_full - avail_floor)
```

## Итоговый рейтинг

```text
если GATE провален:
    score = 0
иначе:
    score = clamp(score_ewma * avail_factor - flap_lambda * flap, 0, 100)
```

По умолчанию `flap_lambda` равен 0.5. Даже при обнулённом результате внутреннее состояние EWMA обновляется: после восстановления нода не возвращается к прежнему рейтингу мгновенно.

## Пример трёх прогонов

Пусть первый прогон дал `S_run=100` и прошёл GATE:

```text
score_ewma = 100
flap = 0
avail = 1
score = 100
```

Во втором прогоне нода недоступна, поэтому `S_run=0` и GATE провален:

```text
score_ewma = 0.3 * 0 + 0.7 * 100 = 70
flap       = 0.3 * 100 + 0.7 * 0 = 30
avail      = 0.3 * 0 + 0.7 * 1 = 0.7
score      = 0
```

Третий прогон снова даёт `S_run=100` и проходит GATE:

```text
score_ewma = 0.3 * 100 + 0.7 * 70 = 79
flap       = 0.3 * 30 + 0.7 * 30 = 30
avail      = 0.3 * 1 + 0.7 * 0.7 = 0.79
avail_factor = 0.725
score = 79 * 0.725 - 0.5 * 30 = 42.3
```

После одного успешного прогона рейтинг восстановится только до 42.3. Следующие стабильные прогоны постепенно поднимут его.

## Что хранится в SQLite

Таблица `scores` содержит одну строку на ноду:

| Группа полей | Поля |
|---|---|
| Идентичность | `crc`, `node`, `provider`, `protocol`, `region`, `country`, `label` |
| Текущее состояние | `active`, `score`, `last_pass` |
| Компоненты | `reliability`, `consistency`, `throttle`, `jitter`, `latency`, `throughput` |
| EWMA | `score_ewma`, `avail`, `flap`, `samples` |
| Тяжёлый тест | `heavy_ok`, `heavy_ts` |

После каждого прогона `Scoreboard.end_pass()` перезаписывает снимок и добавляет строки в `score_history`. Ноды, которых не было в прогоне и которые не сохранены через `keep()`, удаляются из текущего снимка.

Полный DDL приведён в [SCHEMA.md](SCHEMA.md).

## Как рейтинг влияет на переключение

Переключатель рассматривает ноды региона с `score` выше нуля:

- `EMERGENCY` срабатывает по провалу GATE активной ноды;
- `QUALITY` требует преимущества кандидата не меньше `quality_margin` в течение `confirm_cycles` прогонов;
- `ROTATION` выбирает среди нод, прошедших `rotation.min_score`;
- свежий отрицательный `heavy_download` исключает кандидата, пока есть ноды без veto.

## Настройка

Все параметры находятся в секции `scoring` файла `config/config.json`. Их образец и значения по умолчанию приведены в `config/config.example.json`.

- Увеличьте `flap_lambda`, чтобы сильнее штрафовать скачки рейтинга.
- Увеличьте `alpha`, чтобы быстрее учитывать свежий прогон.
- Измените `weights`, если для вашей сети скорость важнее стабильности.
- Настройте `thresholds` под скорость канала и допустимые задержки.

После изменения порогов проверьте несколько реальных прогонов: одинаковый балл при разном наборе метрик не означает одинаковую полноту измерений.
